# 1688 批量导入合同

当前命令为 `cmd/1688-batch-import`，执行与本地队列归 `internal/batchcapture`。它驱动现有浏览器插件和应用确认/保存链路，不增加另一套服务端采集 API、商品事实或发布状态机。

## D1. 输入、身份与浏览器

- 使用明确选定的当前浏览器和本地 profile；页面、验证码与登录交互由当前浏览器链路处理。
- 应用验证后的 actor / Organization 才是批次归属。操作人必须确认应用实际报告的 scope，本地 profile 或命令行期望值不构成授权。
- 源码/工具检查不等于真实1688可用性。批次不会自动处理平台挑战、扩大采集范围或绕过当前权限/资源限制。

### D1.3 确定失败与挑战

确定下架或非法链接可记录为本地失败。验证码、登录挑战、未知页面和外部状态不确定必须停止批次，不把挑战当作已验证的业务失败继续自动推进。

### D1.4 批次 scope

恢复和提交前都比较原 actor、Organization 和确认结果。账户/企业不一致、缺失确认或当前授权不可用时停止，不自动把原批次归给另一个身份。

## D2. 本地持久化与提交边界

本地队列只拥有“原本打算做什么、推进到哪里”的事实；服务端 acquisition operation 仍拥有实际提交和发布结果。

`queued -> submitting -> submitted` 表示本地进度；确定来源失败为 `failed`，可能已提交但无法核实为 `outcome_unknown`。它不是服务端状态机的副本。

### D2.1 先持久化，再 handoff

在可能让应用接收输入的 handoff 动作之前，先将 submitting intent 原子写入并确认 durable。该写入失败时不得 click / handoff。新目录及父目录的持久化同样属于队列保存合同。

只在“确定从未提交”时允许重新采集。导航和本地采集失败不等于提交；一旦 handoff 可能发生、应用 URL 出现或无法核实其结果，后续失败保留 UNKNOWN，停止批次。

### D2.2 原身份回读与恢复

获得 key 后立即绑定到原队列项，按原 actor / Organization / key 回读服务端结果。404、响应丢失和作用域隐藏都不证明没有执行；不能换 key、换账号或重新 handoff 猜测恢复。

队列缺失、损坏、截断或不可信内容整体拒绝，不部分加载后重发。重启只沿可信的原队列状态恢复，不从浏览器历史推导新事实。

## D3. 并发、取消与资源

保持现有单批次推进、锁及原子文件替换约束。同一队列不被多个执行器同时改写。离开/取消停止后续推进，不删除原记录，不推定服务端未执行，也不释放原消费或 UNKNOWN 持有。

平台公开范围、去重/容量和当前计量由既有采集与资源合同决定。批处理不免除服务端权限、资源扣费或显式业务批准。
