# 知识库原文件删除与容量释放 V1

产品决定为用户在 #1103 会话确认的[首版最小范围](https://github.com/henryxu1008/shuomi-ai-commerce/issues/1103)。源码基线为 `e4d440def298e36cb70c261de0c2bad9074a9503`。分类为 **Independent Architecture**。本文定义后续实现合同。架构评审和 UI 准入分别记录于 #1103。

## 产品结果与适用范围

企业管理员可以永久删除本企业一份无需保留、已经计量的知识库原文件，并在原「资源与额度」看到实际用量更新。操作从「AI 工作台 → 知识库 → 我的知识库」的已停用资料进入。确认内容应足以识别资料版本及字节，明确永久删除和完成状态。企业知识库与容量页沿[现行 UI/IA 权威](../product/final-ui-ia-authority.md)、[企业知识库 4703:572](https://www.figma.com/design/tg48P46SSXl6TBy9lZwg63?node-id=4703-572)和[企业存储容量 5872:440](https://www.figma.com/design/tg48P46SSXl6TBy9lZwg63?node-id=5872-440)。本稿提出删除确认和续行的行为合同，具体 UI 增量需在现有 Figma Product Authority 核对确认后实施。

- 首版一次一个 Knowledge Revision，仅覆盖已完成停用、只有一个版本、处理已完成、已确认计量且无依赖的资料。源版本元数据、既有审计事实和停用规则保留。原文件删除不触发解析副本、备份和引用的级联删除。
- 资料仍在使用、有多个版本、被任何冻结上下文条目或历史引用使用、有在途许可或处理、受保留约束、或上传终态不可证时不满足资格。仅知识库停用、版本替换或资料不可读仍沿原计量合同。
- 首版采用已批准的非版本化 MinIO，配置须能证明物理对象不存在。原文件以外的资产、云厂商、批量删除、定时清理、迁移和回填均在范围外。Legacy decision 为 N/A，使用当前领域、当前对象和当前账本。

## 领域所有权与调用关系

| 层 | 权威事实和责任 |
| --- | --- |
| Knowledge | 原资料与版本、历史引用、上传写入证明、唯一删除操作、存储删除证明及操作续行 |
| MinIO 与 S3 适配器 | 同一物理部署、桶和 key 的已确认对象存在性。适配器执行并验证单对象操作，报告确定存在、确定缺失或无法判定 |
| 企业容量 | 原对象的计量身份、字节及分类，已用余额和不可变释放回执 |
| 工作台 | 原权限内显示能否删除、版本、确认与处理状态，沿原容量摘要显示用量 |

调用路径为现有工作台知识库 → 原 BFF 和实时鉴权 → Knowledge 删除命令及 repository → 窄权限 S3 删除/核验端口 → 容量内部 `ReleaseStored` 合同 → 原容量摘要。应用只装配端口。Knowledge 以内部调用持有删除资格和证据，容量端口仅接受可信 Knowledge 调用及已持久化证明。接口和客户端都不提交或决定企业、对象地址、账本字节或存储证明。参见[领域边界](project-boundaries.md)、[知识库生命周期](agent-knowledge-context.md)和[容量合同](enterprise-storage-capacity.md)。

## 企业权限和命令身份

每次预检、确认、状态读取和续行沿知识库现行的实时企业访问门禁。在当前有效企业具备 `workbench.knowledge.manage` 方可操作。平台管理员适用相同的目标企业门禁。切换企业后按原作用域丢弃旧响应。沿已停用资料脱敏规则返回必要版本号、大小和状态，正文、存储地址、凭据与内部证明不进入响应。

- 确认绑定有效企业、固定资料和版本、读到的生命周期版本及命令键。Knowledge 事务内从持久事实读取目标，不接受客户端替换。首次确认必须命中当前版本和资格。
- 在当前企业对命令键唯一约束，保存规范化请求指纹。同键同载荷返回原操作，同键异载荷拒绝。以企业与 Revision 唯一约束聚合不同键对同一版本的并发请求。已有操作的状态回读不受已完成的版本推进影响。
- 发出每次删除前在原作用域重新核对实时权限。存储发送的授权点为授权检查后成功提交的 dispatch 转换。撤权后的调用拒绝；已授权且已可能发送的操作保留原身份，后续由同企业仍有权限的管理员核实。回读和账本续行不依赖原操作者仍在任。记录发起人及执行续行人以便审计。

## 防止迟到上传

已有处理成功、停用和租约到期都不证明旧 PUT 已终结。当前上传在丢失响应后会读回并恢复原版本，底层 `If-None-Match: *` 只能约束对象存在时的覆盖。物理删除后旧 PUT 可能重新创建该 key。[现有 Upload](../../internal/knowledge/service.go) · [ClaimUpload](../../internal/integration/persistence/knowledge/processing.go) · [不可变 S3 写入](../../internal/integration/s3/uploader.go)

Knowledge 在原 Revision 旁保留最小的上传结束事实。只覆盖启用该合同后首次准入的版本。老版本、无证据版本以及曾有未知或多次发送的版本继续按原上传合同服务，首版不可删。

| 写入边界 | 可删证据约束 |
| --- | --- |
| 第一次实际 PUT 前 | 在 Base → Source → Revision 的既有锁序下，核对原租约、当前状态及删除封锁，提交一次性的 `FIRST_PUT_IN_FLIGHT` 记录。仅首次提交成功的当前调用得到发送资格。提交结果不明和进程重启均不把这个资格转给后续调用 |
| 网络发送与回执 | 复用 S3 SDK 的知识库 PUT，证明路径使用单次网络尝试，关闭该调用的 SDK 自动重试并沿直连、禁止重定向的客户端。该发送必须收到可信成功响应，并按原对象校验摘要、字节和原计量绑定。仅同一发送凭证可持久化 `FIRST_PUT_CONFIRMED` |
| 超时、恢复与再发 | 响应丢失、无法确认成功或没有持久化成功凭证的记录不得用于删除。读回对象、旧上传命令重放、处理器恢复和过期租约不能补发该凭证。确需原路径再发时，在同一锁序先把资格永久记为 `INELIGIBLE`，然后才可发送。第一份迟到成功回执不能把它改回可删 |
| 开始删除 | 已有一次成功证明、无其他可能发送的 PUT，且在同一锁序内确认 Source 为 `DISABLED`、版本和引用条件成立，再提交删除操作与永久禁止该 key 再写的标记。上传领取、实际 PUT 准入、恢复和对象身份重绑定均识别该标记。旧成功命令可回读删除状态 |

首版单次网络尝试约束仅适用于知识库的实际 PUT。原上传的应用级续行保留，续行后可正常使用文件，可删资格保持关闭。独立验证必须在传输层统计实际请求，覆盖迟到响应、原命令重放与并发发送。若当前 SDK、HTTP 传输或部署代理无法证明一次真实发送，关闭该部署的删除能力。

### 启用代际与旧写入方隔离

上传结束凭证的信任前提是所有能写入该前缀的应用路径都执行同一发送约束。启用顺序为停止并排空原 Knowledge PUT writer，核对所有 PUT 消费路径均升级，吊销旧写入身份并验证其无法在原前缀执行 PUT，将新写入身份只交给支持该合同的发布实例，最后由部署 owner 在 Knowledge 持久启用本次代际。已有旧写请求只可能针对代际启用前已经存在的版本。凭证只授予新代际启用后由原上传事务首次创建并标记该代际的 Revision，续传、回读和旧版本重放不能补标。采用既有窄权限策略与发布门禁，保持原物理 namespace 和对象所有权。

从首个凭证代际写入起，旧 writer 与仍使用旧凭据的副本不得再次接管该前缀。发生故障可关停新删除入口，保留同代际上传证据、删除封锁与账本回执的识别，已可能发送的删除仍可由兼容程序核实。没有支持该合同的回滚镜像时，停止相关 writer 并修复前进。新凭据分发和禁止回退按发布验收，首版不对现有试用实例做滚动混部验证。

## 删除操作与物理证明

Knowledge 保存一条有界操作，固定企业、资料与 Revision、原物理 namespace、key、摘要、字节、原计量绑定、发起人、命令指纹及状态。所有跨库和对象调用在原数据库事务之外进行。用原状态 CAS 续行，读操作不发起写入。

1. **`FENCED`**。在 Knowledge 事务检查当前权限上下文、资料生命周期、一个终态已计量版本、冻结引用和保留条件。旧许可和处理已退出。写入封锁与唯一操作一起提交。只有已提交的封锁可进入存储预检。锁序与原上传、引用和停用路径一致。
2. **`DELETE_DISPATCHED`**。在同一已验证 MinIO 部署与桶，对精确 key 读到匹配的原对象，核对配置及容量释放的全部稳定前置条件。账本确认目标已入账、原绑定已确认、仅有原绑定且未结预占为零。该代际的 Knowledge 对象只允许其首次绑定的 reservation 重放，拒绝第二绑定。Knowledge 已封锁后不能产生新 PUT 或重绑定。预检后重新核对当前授权，持久化“已见原对象”的证据和发送状态。只有本次 CAS 确认提交且持有效领取的调用可发出 `DeleteObject`。状态提交结果不明时先回读原操作并按恢复路径处理。成功响应、超时或崩溃均按原操作读回核实。发出前已经缺失的对象进入异常核实，不能生成释放证明。
3. **`OBJECT_ABSENCE_PROVEN`**。在同一固定端点上复核原 namespace 和桶状态。取得已授权的精确 key `HeadObject` 缺失以及同 key 的 `ListObjectVersions` 完整、未截断且无实体版本和删除标记的结果。持久化带格式版本的证明摘要，绑定原删除操作、原先存在证据、发送事实、原物理身份、原文件摘要/字节和读回结果。可信的读回可处理 Delete 响应丢失。权限错误、桶缺失、网络异常、版本/标记仍在、分页不确定、对象不匹配或身份漂移均保留待核实。
4. **`RELEASED`**。持久化证明后调用容量内部端口。回读或收到原释放回执后，在 Knowledge 保存回执并显示完成。原资料保持停用，保留原文件操作和审计记录。

物理删除的计量含义为原计量 namespace 的文件对象已不存在。首版只接入能验证部署 ID、桶和精确 key 的受控非版本化 MinIO。版本化或挂起版本化、保留策略、对象锁或外部 lifecycle/复制等可影响该前缀的写删路径均不准入。部署 owner 保证桶在启用代际和未结操作期间不被重建、调换或恢复到原命名空间，配置或身份变化即停止发送和释放并重新核验。该不变量与禁止其他写删路径同属受控存储的准入。复用现有私有直连与 [MinIO 部署身份校验](minio-capacity-admission.md)。删除执行身份与原普通读写身份分开，只具对应私有前缀的 Delete 和核实所需读权限，无广域删除、版本删除或保留绕过权限。[MinIO 固定版本删除处理](https://github.com/minio/minio/blob/RELEASE.2025-04-22T22-12-26Z/cmd/object-handlers.go#L2331) · [MinIO 版本与删除](https://docs.min.io/aistor/administration/objects-and-versioning/object-delete/)

## 容量只释放一次

`CloseWrite` 收回未使用的预占。新的内部 `ReleaseStored` 只接受原 Knowledge 操作固定的已持久化删除证明，消费原容量对象行。复用企业账户事务锁 `Repository.locked`。对账本中的 `namespace + key` 对象身份、企业、原已确认写绑定、摘要、类别 `knowledge_document` 和字节逐项核对。要求原单对象写入绑定已确认、无未结预占、无其他绑定，账户余额足够。遇到冲突保留原事实并等待核实。

- 账本用原对象行保存释放操作 ID、证明摘要及完成时间，作为唯一回执。一个事务将该行从已入账变为已释放并减少账户已用字节，原摘要按已入账行聚合分类。可用量按现有 `max(quota − occupied − reserved, 0)` 计算。
- 同一对象同操作同证明返回既有回执。不同操作或不同证明拒绝。保留已释放对象行，`BindObjects`、原写入查找、发送准入和 `ConfirmStored` 在任何成功重放前拒绝恢复该身份。预占、扩容包、钱包和其他分类沿原 owner 与事务。
- 没有成功释放事务时，旧占用继续有效。释放事务已提交而 Knowledge 尚未记录回执时，容量页可能已显示下降，操作页显示待确认。续行查询原释放事实，不再次扣减。回退能力按上传凭证代际判断，早于第一笔删除。释放之后的程序同样必须保留原对象封锁与回执识别。[原账本事务与摘要](../../internal/integration/persistence/storagecapacity/repository.go)

## 失败、重试与验证

| 失败点 | 结果与续行 |
| --- | --- |
| 权限或资格拒绝、确定尚未发送 | 不删对象、不改账本。对已保留的操作可由有权管理员继续，重查发送资格 |
| 已授权发送，响应不明、重启或并发请求 | 原版本持续封锁，账本保留占用。原操作先读回。对象仍存在且可确认身份与当前资格时，原操作才重发同一个 key。并发续行使用原操作的有限领取。已过期的领取不能变更数据库状态。迟到 DELETE 只作用于同一永不复用的 key |
| 已核实对象缺失，存证明或账本调用失败 | 重启后沿原状态再次核实，已持久化证明的情况只重放或查询原释放。账本确认前不显示「已释放」 |
| 容量提交后回包丢失或 Knowledge 写回失败 | 原对象回执重放，补写原操作完成状态。已用字节只扣减一次 |

首版恢复入口为管理员「继续核实」，由 Knowledge 处理原操作。网络和事务采用现有有界超时，每次续行仅核实一个对象。依赖异常期间保持明确的待核实状态。页面提示语区分「删除待核实」「原文件已删除，容量待确认」与「已释放」。

- **正常路径**。在可销毁环境使用固定 MinIO 和真实 PostgreSQL。上传已知字节、停用、删除、核对原对象确实缺失、回执与原用量差值。其他文件和企业数据及分类用量不受影响。
- **迟到写入**。在实际 SDK 传输层统计发包，模拟 PUT 成功响应丢失、重复命令和迟到 PUT。证明未闭合的版本不可删，确认封锁后不会有旧操作重新 PUT 或重新入账。
- **删除证明**。覆盖错误部署、权限错误、超时、缺失桶、删除前已缺失、版本化/挂起版本化与删除标记。只有经受控存储核实的目标进入释放。
- **并发与恢复**。重复请求、同键异载荷、跨企业、权限撤销、历史引用存在、对象删除响应丢失、账本提交响应丢失、两库各自重启。断言回执与原身份一致，账本只扣减一次，原资料不会恢复可读。确认功能关闭时原上传与计量可用。另验证启用前代际的旧凭据 PUT 被拒绝、旧版本不能取得可删凭证、关闭删除入口后仍无法以旧 writer 接管。

当前架构审查使用静态证据。实现、隔离环境执行和试用验收均为 `NOT_RUN`。
