## 1. 用户结果和范围

当前企业内有相应权限的成员，可以在硕米 Chat 选店铺，从技能库选择官方「创建技能」，用一句需求起草一个个人文字版标题技能。用户编辑、核对并明确保存后，可在「我的技能」找到该私有草稿。既有标题技能后续沿第 2.2 节进入原标题处理页。项目创建和管理从项目中心进入；Chat 不再展示「项目操作」选择入口。已有项目会话仍可继续处理单项商品内容任务，按需手动关联到项目详情。

首批先交付「创建技能」。创作产物为一个仅含 `SKILL.md` 的个人标题技能私有草稿，脚本、附件、图片技能、团队技能创建、批量创建、自动发布、启用与共享均在首批文字创作范围之外。后续脚本创作见第 2.3 节。已有标题技能接入时，候选来自已启用的商品标题整理、标题本地化、冗长标题精简以及当前获准的个人、团队标题技能。已有图片技能使用原图片入口。原项目任务仍为单项、单商品，普通 Chat 规划与既有项目会话分别保留各自输入。

## 2. Chat 中的共同入口

- 在新对话和支持对应操作的会话输入区，「选择店铺」与「选择技能」紧邻放在同一行，空间不足时自然换行。右侧抽屉先接入官方「创建技能」，具体行为见第 2.1 节。Chat 不再提供「项目操作」选择入口；已有项目会话与原请求恢复仍沿原合同。普通消息、技能创作和标题处理分别由各自按钮触发。
- 店铺候选复用 Chat 的已连接店铺选择器。按当前身份读取可见且已确认连接的店铺，列表部分不可用时说明原因并提供重试。没有可选店铺时，可前往现有店铺中心完成连接后返回。取消店铺后，卡片显示本次没有选择店铺。
- 创建项目取决于项目中心是否可用及当前成员能否管理项目，保存项目无需模型就绪。执行项目任务取决于项目读取、Chat 使用及现有商品内容规划和执行能力，具体商品及店铺还须分别授权。「创建技能」按当前企业的 Chat 使用、模型路线与个人技能创建条件开放。后续标题候选使用原商品标题能力和权限。能力暂不可用时显示原因和可采取的操作。
- 草稿按当前账号、企业、会话或新建入口保存。在提交前可修改或关闭卡片，关闭卡片不提交，普通消息草稿可继续编辑。切换账号或企业时清除旧范围的可见选择及迟到响应。键盘可以打开和关闭选择器、修改表单并到达主按钮，窄屏时允许换行，完整显示当前选择与错误提示。

### 2.1 用「创建技能」起草并保存个人标题技能

> 本节记录首批文字候选的行为和验收。后续「创建技能」的点数展示按第 2.3 节的统一规则，适用于文字和含脚本的个人标题技能。

1. **选择技能并填写用途。** 抽屉从技能库读取已开放的官方创作技能及其准确版本，显示「创建技能」及「生成个人标题技能草稿」。选定后收起抽屉，在 Chat 展示创作卡。用户填写目标、输入、处理规则与输出示例中的必要内容，首次只需一段说明。从新建入口进入时先按原流程开启会话并带入未提交说明，创建结果不明时沿原键核实。准备输入、选择版本和开启会话只准备后续操作。
2. **核对费用后生成。** 点击「生成草稿」前，卡片显示由当前企业现有计价服务提供的本次点数上限，注明重新生成是另一次授权调用。用户点击后提交同一版本、明确的文字说明和报价引用。工作台核对当前身份、会话归属、模型开放和技能版本，冻结本次输入；报价、版本或运行条件已变化时，展示新状态并让用户重新确认。没有已开放模型、有效价格或可用额度时显示可处理原因。生成使用原受控文本模型与点数体系，每个生成请求最多一次模型发送。
3. **人工编辑和检查。** 成功后显示名称、用途与可编辑的文字说明。输出是供审核的建议，程序用固定字段装配一个标题用途的 `SKILL.md`，使用现有包校验器检查结构、大小、支持的文件和链接约束。模型只接收本次提交的说明与官方创作技能内容。用户对说明中的实际业务规则负责，界面区分格式通过与内容已审核。格式不通过时保留可改内容，用户可以修正后再检查。正常刷新可读取已生成草稿，页面内未提交的人工修改在当前编辑页保留。关闭已发送的卡片后，可以回原会话查看生成与计量状态。等待保存的确认内容按下文恢复。
4. **确认保存到「我的技能」。** 卡片展示最终名称、用途、内容和归属。用户点「保存到我的技能」后，才沿现有个人技能创建命令保存为 v1 私有草稿。保存前重新校验人工编辑后的完整内容和当前身份，每次编辑使前一次格式检查失效。取得原技能回执后显示「已保存到我的技能」及详情入口。发布、启用及在当前企业使用，继续由技能库原有流程处理。编辑、格式检查与保存均不调用模型或扣生成点数。

**用途和授权。** 「创建技能」是 Skill owner 保存的可追踪官方版本，技能用途为技能创作，产物用途固定为商品标题。现有 Skill 识别标题和图片，需要新增明确的官方创作用途及其授权候选。官方版本的注册、发布和启用走原平台维护权限。仅预先批准的官方创作技能可由此路径消费，普通个人或团队上传的包不能获得创作权限。创作技能从标题、图片入口的候选中排除，用户生成的包只按标题技能规则保存。浏览器选择只用于说明用户意图，实际版本由 Skill owner 解析并在模型发送前复核。当前选店和项目只是 Chat 背景，创作模型的输入限用户本次说明和官方创作材料；商品、店铺、项目资料、团队技能正文、会话其他消息、文件、工具与外部链接均不自动附送。企业负责本次模型的授权和点数，个人账号持有已确认保存的技能。切换企业或账号时撤下旧卡片与候选，请求和结果仅在原账号、原企业和原会话重新授权后展示。已保存个人技能仍按原个人技能库合同读取。

**运行与计费。** AI Workbench 持有有范围的创作生成命令和生成结果，沿现有命令冻结、原键重放和有界终结方式实现专用用途。当前 Chat 命令库及模型操作只识别登记用途，需要为创作登记命令、受控文本报价和调用记录用途、企业路由、点数业务范围与用量展示。创作调用归原工作台创作命令，普通 Chat、商品内容规划和提案走原路径。受控文本报价提供输入及输出 token 上限，界面用同一冻结资费和预留算法计算点数上限。报价绑定当前账号、企业、成员、会话、完整输入摘要、创作版本、路由和价格版本、上限及有效期。点击生成后先按原键登记这组已确认的参数，受控发送在调用前复查。技能生成结果与生成命令完成状态同事务提交。原 AI 和点数 owner 负责预留、使用量结算及用量读回，Skill owner 负责技能保存及原回执。

Chat 页面经现有 BFF 访问按会话授权的创作报价、生成、保存与状态读取。写入沿原命令键执行。Workbench 创作服务复用现有应用装配注入的企业文本路由和执行器，以及 Skill 服务的官方版本解析、包校验及个人保存。报价和状态读取只返回当前权限允许的值。计量展示以原点数预留及结算事实为准，单独的模型调用记录只用于核对原调用状态。模型已返回而结算未确认时，页面显示计量待核实。

| 情形 | 用户看到的结果与恢复动作 |
| --- | --- |
| 生成明确未发送 | 显示未生成和可修正原因。只有原计量机制确认未发送且预留已释放，或在预留前已明确拒绝，才显示本次无扣点。再次生成须由用户触发。 |
| 模型已响应但输出无效 | 保留原说明，说明草稿未生成。若计量确认了模型使用量，沿原规则结算并展示实际结果；计量未确认时显示待核实。重新生成需使用新的明确确认和请求键。 |
| 生成结果、响应或计量未确认 | 刷新或重进原会话后可「核实原生成请求」。先按原键读取生成结果及原计量状态。仅在原调用 owner 能证明未曾认领、且原报价、权限和时限仍有效时，同一请求才可继续原发送流程。已认领的模型请求进入原核实、结算或有界结果未明状态，始终沿原调用核实。模型结果已结算但草稿提交丢失时如实显示两侧状态。 |
| 保存被拒绝或结果未确认 | 确认保存先在 Workbench 的同一草稿范围原子登记唯一保存意图、保存键及最终确认内容，再调用现有个人技能创建。并发或迟到提交即使带了其他键，相同内容也沿用已登记意图，内容不同则提示原保存状态并拒绝覆盖。Skill owner 在原事务内用登记的键保存一次并写回回执。保存或响应中断时，刷新显示原状态。用户回到原会话点击「核实原保存」，工作台重新核验本人、原企业和会话权限后代理同一键和原内容。Skill 服务先读同键回执，无回执时继续完成原先确认的保存。只有确知原意图未受理时，才允许用户修正并明确提交。结果不明或当前权限失败时保留原意图。 |

生成请求与保存请求各用独立的键。Workbench 按原账号、企业、会话保存本次有界输入和生成结果，官方技能材料由原不可变引用读取，浏览器仅保留恢复指针。保存确认到达并冻结后可以跨刷新恢复最终编辑内容。服务端尚未接收时，刷新后显示已生成的原稿，并提示尚未保存。Workbench 保留已确认保存的有界请求输入至核实完成。保存成功后，该创作草稿固定关联 Skill 原回执和已确认内容摘要，旧提交继续返回同一结果；用户后续修订通过「我的技能」保存新版本。Skill owner 持有技能版本和原回执。两个事务之间使用原键核实和收敛，当前余额与用量从原计量读取。用户说明沿现有 Chat 的 8192 UTF-8 字节上限，单一 `SKILL.md` 沿包校验的 16 KiB 上限，且受所选路线的更严格输入与输出限制。超时及结果未明的终结沿现有受控文本和 Chat 命令的时限与宽限。

### 2.2 从 Chat 选择已启用的标题技能

1. **打开右侧抽屉。** 按当前账号和企业读取技能库的标题候选，显示名称、来源、版本和用途。团队技能须为当前团队已共享且可用的版本，个人技能须为本人已启用且获当前企业准入的版本。标题入口未开放、无权限、无候选和读取失败分别给出真实状态，读取失败可重试。键盘关闭抽屉后焦点返回按钮，窄屏可查看候选并操作。
2. **暂选一个具体版本。** 选定后收起抽屉，显示技能名称、版本、「待使用」及「前往标题处理页」。可再次打开抽屉更换或取消。选择仅用于这次标题处理，普通消息和项目任务各用自己的有效输入。打开、选定、取消和前往标题页都是准备动作，产生的请求仅限读取当前候选和导航所需资料。
3. **选择商品并在原页面确认。** 点「前往标题处理页」后复用已有自有商品搜索和选择，随后打开原商品标题优化页。页面显示来自 Chat 的选定技能及版本，确认时核对商品、目标语言和技能版本。用户在原确认流程明确提交后，才按原内容 Agent 路径生成建议、计费、审阅与采用。Chat 的店铺为会话背景，标题路径按当前企业和商品权限读取与处理自有商品，目标语言由用户决定。如果界面展示来源店铺，标为「Chat 会话店铺」，商品归属和执行参数继续由原流程确定。
4. **留在同一工作范围内返回。** 返回原 Chat 会话或新建入口时，沿原草稿机制恢复未提交的聊天输入。技能尚未提交时，同账号、同企业、同入口下显示原待使用选择并重新核对版本。标题提交已发出时，按下文规则回原入口核实或查看结果。再次准备标题任务需要主动选择。返回路径由已验证的 Chat 路由生成，进入会话仍校验当前读取权限。切换企业或账号时撤下旧商品和技能选择、丢弃迟到响应，并按新范围重新读取候选。项目改绑后的新会话按第 4.1 节接收未提交的项目需求草稿，旧技能选择与旧请求留在其原作用范围。

导航携带原用户、原企业、标题用途及准确技能引用（技能 ID、版本、摘要）。复用现有标题技能候选、商品选择和原标题确认。当前官方模板的「选择已有商品」入口只接受官方版本，Chat 入口复用商品选择，并按相同标题候选服务复核可用的官方、个人和团队版本。官方入口的来源限制仍适用于官方入口。导航信息只表达用户选择，业务权限、版本状态和商品授权均由原服务当前核验。

在打开商品选择与确认时重新核对原版本。Chat 进入的新确认只接受带入的同一技能 ID、版本和摘要。已停用、撤权或与原摘要不符时，按当前可披露权限显示原选择及不可用状态。无法读取时提示重试。需要更换或取消时返回 Chat，由用户更改待使用选择。原独立标题入口继续提供自己的技能选择。

原标题页保存原请求的恢复位置时，为同账号、同企业、同 Chat 入口和同浏览器标签页保留这条导航引用。再次从原 Chat 打开同一标题操作时，进入该原标题页，核实原请求或查看原结果。导航引用只指向经校验的站内原标题恢复地址，标题运行状态、请求和回执继续归原标题流程，Chat 草稿只保存未提交的输入和选择。

标题页核实待决提交时使用原请求和冻结版本。新选择的候选校验只用于新确认，原回执读取依据当前原请求披露权限。结果仍不明时保留原核实入口；若涉及新的执行效果，仍通过原标题运行的当前权限与技能状态校验。Chat 原会话的创建、规划和确认分别沿第 4.1 节和第 6 节恢复。

### 2.3 「创建技能」生成带脚本的个人标题技能

> 2026-11-17 用户确认的后续增量。创建保持「说需求 → 看草稿 → 保存」，Agent 可以起草 Python。第 2.1 节保留首批文字候选的合同和验收证据。脚本执行沿 [标题技能脚本合同](skill-script-sandbox.md#5-技能包运行-profile-与权限)。本节是新创作能力的独立设计依据。

**产品范围。** 产物仍是本人「我的技能」中的私有商品标题技能。草稿可只含文字，也可包含一个用于候选标题后处理的离线 Python 入口。首批脚本创作支持由 Agent 生成、查看和修改代码。脚本使用现有固定 Python 标准库和标题 JSON 输入输出。Shell、依赖安装、自选命令或镜像、外部连接、图片或团队技能、创作时试运行、自动发布或启用均不在本增量。已保存脚本首次运行在原商品标题处理入口完成。

#### 用户操作

1. **说需求。** 从选店旁打开同一个「选择技能」抽屉，选官方「创建技能」。例如输入「把候选标题里连着的空格合并，保留品牌和型号」。需求填写后，卡片在后台自动核对本次点数，准备好后显示主按钮「生成草稿」。用户可以直接编辑需求，系统重新核对。报价加载失败时显示可重试的提示，旧报价不可用于生成。点击「生成草稿」才授权这次模型调用。
2. **看草稿。** 同一卡片展示名称、用途和规则。模型根据本次需求建议是否包含脚本。含脚本时，在保存按钮附近明确显示「包含 Python 脚本」，附上对本次用途的草稿说明和可用键盘展开的「查看代码」。用户可直接改文字、展开改代码、移除脚本，或输入一句「让 Chat 修改」。系统为这次修改自动核对点数。点击「生成修改」才调用模型，成功后刷新草稿供核对。手工编辑和自动格式检查免费。格式问题直接指出对应字段，校验采用现有包规则，未通过时保存不可提交；校验通过表达格式结果。
3. **保存。** 卡片显示最终内容和「保存到我的技能 · 个人私有草稿」语义，用户点「保存到我的技能」即确认最终内容。有脚本时展开区及保存状态继续标明是否包含脚本。成功卡显示「查看我的技能」。退出或折叠收起卡片，回原会话可读取之前生成的版本和待核实请求。未提交的手工编辑在当前编辑页保留，服务端已受理的保存可以跨刷新核实。

**点数展示。** 首次和后续使用都以「生成草稿」或「生成修改」作为操作入口。Chat 创作卡片不展示预计或实际点数，也没有「费用详情」。已产生的消耗从现有「用量明细」里的「创建技能」使用记录查看，沿原企业、当前成员访问权限和账本读取。Chat 只在额度不足、无法计价或结果待核实时提示当前状态和可采取的操作，无金额提示。每次生成仍在后台核价并检查额度，由用户主动点击发起。

**实际使用。** 用户从个人技能库沿原流程发布、启用并满足当前企业准入，再在原商品标题处理页选定准确版本，核对商品和报价后启动。模型先产出标题候选，既有沙箱消费固定 JSON，页面展示前后结果。原默认模式人工采用，只读模式查看。原标题运行仅在当前成员权限、企业与版本准入及沙箱开放条件均满足时执行。沙箱与标题任务的失败、清理、计量和不明结果统一由原标题流程处理。Chat 的草稿与保存接口没有脚本执行权限。

**请求和输入边界。** 模型按严格的结构化结果输出名称、用途、规则及可选的脚本用途说明、Python 源码。服务端固定用途、路径、执行配置及输入输出合同，不接受模型或浏览器自定 manifest、工具、外部 URL、镜像或执行参数。文本和文件结构复用 Skill owner 的现有包校验；脚本用途说明是可核对的草稿内容，程序不从自然语言或代码关键词判断业务正确性。手工修改脚本会清除旧的脚本用途说明或标明需人工更新，保存前始终按实际包内容判断是否含脚本。模型只接收官方创作材料和用户当次提交内容。修改时可一并送当前草稿的说明和代码，送出前卡片展示其范围。店铺、项目、商品、其它会话消息、凭据与文件系统均不被选入。输出、历史和预览视为普通文本，代码不作为工具调用解释。每文件 16 KiB、完整包 48 KiB、请求 96 KiB；创作 JSON、命令输入和模型输出亦受本次已配置上限约束。输入或保存包超限时在发送或写入前给出可修正提示。模型输出超限沿原无效结果及计量处理。

**自动报价。** 服务端沿原模型计价计算短时有效的签名报价，绑定身份范围、命令键、准确版本、完整输入摘要、价格及上限。稳定输入后自动查询，忽略过时响应。报价不保存用户草稿或逐次输入，也不预留点数。显式确认时提交原引用及完整原输入，现有受控计价重新计算并核对签名、有效期、版本及摘要。Workbench 先按原键原子登记已确认请求和输入，再允许模型发送。核对当前范围和原输入后，命中已登记的同键同内容时先恢复原命令，再按原命令状态判断是否仍可首次发送。签名更新或报价过期不影响原回执的查读。同键异内容冲突。确认请求没到服务端时，保持同一页面可用原报价与原输入重新提交。刷新仅保留原键指针，先只读核实；在原确认仍可能受理时显示等待核实。创建命令和判定报价已过期且未受理，复用 Workbench 现有按范围和原键的事务锁互斥检查，以数据库时间在登记处校验过期。只有已过期且确认无原命令后，才允许重新核对点数并确认。服务端签名密钥轮换或重启后，未确认的旧报价可以重新取得，已经登记的请求依原范围和版本恢复。首批文字版的持久报价按原合同处理。

**状态、并发与恢复。** 每次 Agent 生成或修改有独立原键、已确认输入和账本记录。一次创作的第一条草稿作为根，后续修改指向同一根与开始前的有效修订；每个修改确认带原基础修订和本次完整快照。报价只读核对草稿仍可修改。确认修改时，在 Workbench 的同一草稿根事务内校验本人、会员、当前基础修订和未登记保存，再将原报价推进为已确认。复用受控文本执行的预留前和最终发送门禁。最终派发门禁与保存登记、修订推进以同一草稿根行串行核对。此前已保存或已推进修订的修改不发送模型，已有预留由原点数 owner 释放。先获最终派发准入、随后出现保存或修订竞争时，按原调用的实际使用量和回执核实结果，迟到修改按下面的事务规则处理。草稿根的事务不跨模型调用。根只有一个可保存位置。修改完成时在 Workbench 同事务持久化结果，并且仅当基础修订仍是当前、根尚未登记保存时推进当前修订。两个标签同时修改，迟到结果可通过原请求核实，不能替换已经更新或确认保存的内容。界面如实展示其处置与原计量状态。同一标签提交修改时冻结本次输入，当前未提交编辑在确定未受理时可继续。

点「保存到我的技能」提交当前修订引用与最后编辑后的草稿字段。服务端装配完整包，Workbench 在草稿根上原子检查当前修订及会员，登记唯一保存键、完整包的规范内容和摘要，再调用 Skill 原事务。保存先登记则修改结果不能推进，修改先推进则旧修订提交返回冲突并可读取当前稿。不同标签以不同键保存相同包用首次登记的键和原回执，内容不一致仅能读原状态。保存回执确定前保留完整包；核实原保存重放该包，禁止以生成文本重新推导，已确定成功后沿原流程清除待保存内容。增量使用显式的输出格式和待保存包格式版本。未标注格式的首批记录固定按 v1 单文字文件识别，显式未知格式拒绝解析。按记录版本解析旧待保存内容并沿旧键和摘要核实；新版保存的是有界完整规范包，一律使用原登记内容，禁止按当前官方版本猜测或重新装配旧数据。若首批创建的旧草稿已有当前修订变化，缺少修订引用的旧保存不得新登记，已存在的原保存仍沿同一根与回执核实。既有生成回执仍按冻结的原格式读取，过期或版本失效的未发送请求必须重新确认，已认领的请求始终按原账本核实。

切换账号、企业、会员或会话时，撤下旧草稿和报价并丢弃迟到展示。恢复回原范围后先重新校验当前访问，刷新只读。报价过期、原调用结果不明、模型输出无法组成合规包、保存未受理及保存结果不明，沿第 2.1 节显示对应状态和原请求入口。只有原执行组件证明原模型请求未认领且原确认仍有效时，同键核实可首次发送。进入新调用须取得本次有效报价并由用户明确点击；金额按上面的点数展示规则呈现。编辑、检查、保存和核实保存不调用模型。

### 2.4 在同一 Chat 中自动调用或主动选择创建技能

Status: `IMPLEMENTATION_READY`。2026-11-18 用户明确要求：直接发送需求，由 Chat 自动调用技能；同时保留主动选择技能。该决定替代创作时必须点击「进入技能创作」及填写第二份需求的交互要求。独立复核已通过，见第 8.4 节，按本节冻结边界实施。

#### 用户结果、范围与现有合同

- 普通 Chat 中发送「帮我创建一个保留品牌型号、用 Python 合并空格的标题技能」，同一次发送返回可编辑技能草稿。首次发送包含开启会话和处理该消息，不能要求用户再发送一次。
- 「选择技能」保留在选店旁的右侧抽屉。主动选官方创建技能后，仅设置当前输入的技能选择；发送时执行准确版本，跳过自动意图识别。选择本身不创建会话、不生成、不扣点。
- 结果是对话中的草稿卡片，复用名称、用途、正文、可展开 Python 与人工编辑。只有点击「保存到我的技能」才保存个人私有草稿。卡片的「让 Chat 修改」把准确草稿和修订放入同一个聊天输入框的回复背景，发送后复用原修订命令，不另设需求文本框。
- 自动与主动两种方式都复用第 2.3 节的个人标题技能、单个离线 Python、格式检查、原保存意图和用量合同。自动模式只有已开放的官方创建技能；不开放团队/图片技能、脚本试运行、自动保存/启用/发布、项目操作或通用多工具循环。
- 已有明确商品对象的内容任务继续走原规划入口。普通聊天的识别仍支持原店铺概况、商品任务引导和补充说明；新增创建技能。店铺选择不是技能输入来源，不把店铺、项目、商品或其他聊天历史自动塞进创作提示。
- 缺少必要目标或无法判断意图时，模型要求补充；程序不以关键词、语义正则或第二个模型替代用户意图判断。主动选择具有优先级，不被自动分类覆盖。

当前依据为用户上述两项决定、第 2.3 节、[Chat 原始草稿和请求恢复](chat-compose-before-create.md)、[当前会话范围](ai-workbench-work-scope.md)、[领域 owner 边界](project-boundaries.md) 与现有受控文本/资源账本合同。既有未决请求按原操作恢复，不升级其输入或补发未获授权的模型调用。

#### Owner、消费链及最小复用

`Chat 同一输入框 → Workbench 消息命令 → 既有 Eino 意图识别 → 唯一创作子请求 → 既有 governed authoring → 草稿卡 → 原 Skill 创建命令`。

- Workbench 仍是消息、意图命令、消息到创作请求关系和保存意图的唯一 owner。复用当前 `commands`、`messages` 与 `skill_authoring_drafts`，不新增第二套 Agent 会话、技能库或任务调度器。
- 现有 `chat_intent_route` 已处理店铺概况、商品任务和补充说明。沿这一意图识别 owner 扩充闭合决定 `CREATE_TITLE_SKILL`，复用 `einorouter`、模型路由和已有调用认领/结算；当前代码名 `StoreRoute` 不是创建一个平行路由服务的理由。新输入采用明确版本和受控用途 `aiworkbench_chat_intent`，既有 `aiworkbench_store_route` 用途及原端点继续履行自己的当前合同；这是同一 owner 的两个明确调用用途，不是双写意图结果。旧已登记命令用原冻结提示/格式继续读取和恢复，无新请求失败后回退旧调用，也不替换原用途配置。
- 自动模式在首次接纳时冻结当前可用官方技能引用及可用工具集合，模型只返回受限意图，不返回身份、模型、价格或执行参数。手选引用来自同一技能库目录并进入请求指纹。创作需求保持原消息文本；修改的快照只能来自用户在卡片主动选择的准确草稿。
- Skill 仍持有个人版本；AI Capability 持有模型调用和拒绝证明；资源 owner 持有预留、扣除与返还。App 只装配现有 owner 和实时授权，不以 HTTP handler 建立另一事实源。新业务规则放 Workbench service/ports，SQL 放原持久化适配器，模型调用放原 governed adapter。

#### 请求和展示合同

普通发送使用 `POST /chat/conversations/:id/turns`，请求头沿原幂等键，正文为 `content` 加可选的准确 `skill:{version,digest}`。卡片「让 Chat 修改」另带 `revision:{root,baseRevision,snapshot}`，须同时带准确技能引用；缺少明确回复背景时不推测要修改哪份草稿。正文沿原 96 KiB 上限，文字不超过 8192 字节，快照沿第 2.3 节限制。

`GET /chat/conversations/:id/turns/:key` 只读原消息及子请求状态；`POST .../:key/recover` 要求空正文，核对原消息，并仅按原已登记授权和期限继续原一次交接或首次派发。写入沿 `workbench.chat.use`，读取沿 `workbench.chat.read`，均核对当前真实会员与原会话授权。新发送不失败后回退旧 `store-route` 或自动重复消息。已经登记的旧操作仍使用其原端点与原输入。

返回稳定的 `state`（`PROCESSING / COMPLETE / FAILED / UNKNOWN / NOT_STARTED`）、已确认时的 `kind`，以及可选的原 `authoring` 回执。`COMPLETE` 对创建技能只表示已经取得完整草稿，不能把「识别完成」当作「技能生成完成」，保存状态仍由原回执表达。店铺概况、商品任务引导与补充说明沿原消息展示。技能回复是对原消息命令的引用，编辑、核实和保存复用原创作接口；正常历史读取不发模型或写技能。

#### 同库关系与原子交接

这是意图识别完成后继续执行创作的新交接边界，不能仅用浏览器跳页或自动点击「生成」连接。新增有界字段只承载当前功能：

1. 命令保存带版本的冻结输入：自动/主动选择、官方技能版本摘要，以及显式回复草稿时的根、修订和快照。请求指纹覆盖原消息和主动选择；相同键不同内容、选择或快照冲突。服务器冻结的可用技能目录不是第二份技能事实，只是本次调用输入。
2. 命令的创作交接状态为 `PENDING`、`BOUND` 或 `NOT_STARTED`，并保存唯一 `tool_key`。一条消息至多绑定一个创作根或修订；关系由命令 owner 负责。聊天回复只保存该命令的中性引用，草稿状态和正文实时从原创作 owner 读取，不复制技能事实进消息。
3. 自动识别确定创建技能，或手选合法创建技能后，登记 `PENDING`。在父命令锁内检查当前身份、原会话、固定接纳期限及未绑定状态；创作的纯准备完成后，同一 Workbench 数据库事务创建 `READY` 子请求并写 `BOUND/tool_key`，不在事务中调用模型或跨 owner 写入。
4. 候选子键为服务端 UUIDv7，报价期限沿第 2.3 节。并发准备允许产生未使用候选，但只有赢得父锁的候选能写入并发送。已绑定时直接读取原子请求，不重新报价、换版本、换键或延长期限。
5. 首次接纳以数据库时间固定创作接纳期限，最长沿原五分钟报价窗口；子请求 deadline 不超过该期限及其原模型 deadline。父请求未绑定且期限已过时，持父锁证明子请求不存在后转 `NOT_STARTED`，不因重试重新开启窗口。临时读取失败不冒充未开始；权限/技能撤销则拒绝新的交接。无后台自动重发或新 reconciler。

具体关系字段为 `commands.turn_input`（带版本冻结输入，含用户选择与服务端可用技能引用）、`commands.tool_state`、`commands.tool_key` 以及 `messages.turn_key`（引用消息命令）。`tool_key` 仅在 `BOUND` 非空，父命令与技能草稿之间有同企业/账号/会话外键及唯一关系；消息保存父命令引用，不再保存另一份子键或草稿。`turn_input` 的用户输入部分参与指纹，服务器接纳时冻结的目录不在重放时重新生成。新版本请求不可把同键的原版本命令当作新消息。

关系字段、检查约束、唯一约束及同库外键由现有 Workbench schema owner 显式安装并校验，runtime 仅取得必要列权限；普通应用启动不做 DDL。已确认能力没有历史回填、双读双写或旧系统迁移。本次只是当前 schema 的有界加法，保留现有数据和仍有效请求。

#### 状态、失败和首次发送恢复

| 边界 | 结果和唯一恢复入口 |
| --- | --- |
| 新会话首次发送 | 在既有 `PendingCreate` 同时保存独立的消息键、原文本及可选技能。会话创建后用同一消息键继续；响应丢失时恢复原会话和原发送，不再生成新键。没有该发送标记的既有创建请求只按原合同开启会话，不能补发 AI。 |
| 自动识别未发送/无效/未知/结果丢失 | 复用原冻结识别调用、数据库期限和可信回执。未得到有效创建决定时不创建技能子请求；未知不换键重识别。手选跳过这次模型调用。 |
| 有创建决定但子请求未绑定 | 普通读取不执行。原发送内继续或用户显式核对原发送可在原期限内完成唯一交接；过期且证明未绑定后只报告未开始。 |
| 子请求已绑定、HTTP 响应丢失、页面刷新或双标签 | 先读取父命令原 `tool_key`，再沿现有创作恢复。原调用认领、点数和保存意图保持，不产生第二份草稿或重复调用。 |
| 草稿编辑和保存 | 编辑不发模型、不保存技能；修改通过同一聊天输入明确发送准确快照。保存使用原 revision、完整包和唯一保存意图；未知保存继续核实原包，不能把一句「保存」自动当作保存授权。 |
| 切换企业/账号/会员、关闭页面或权限撤回 | 查询与迟到结果仍绑定原身份、企业、会员及会话。浏览器停止显示旧范围；服务器在接纳、交接、派发、读取和恢复实时检查原权限。取消或断连不证明没有调用。 |

历史消息中的技能引用按原范围与当前可见性读取单个原回执，不受最近八项草稿列表限制。读取不派发；原消息核对 POST 才可依据已登记授权继续，原有生成/保存核实入口同时有效。

#### 计费、权限和资源边界

- 发送是本次自动判断和创作的明确操作。自动模式识别与实际生成分别沿各自的原调用、冻结资费和实际用量计量；手选没有额外识别调用。Chat 首次和后续都不展示点数金额，实际消耗进入现有用量明细，不把一次识别或一次生成重复记账。
- 仅复用原有模型额度、月度成员限制、请求字节、输出、deadline 和最大点数准入。新增识别提示/格式须作为准确模型配置接入，未配置就报告不可用，不暗中换 provider 或吞掉失败。
- 创建技能和新识别路径的已证实 OpenAI 预执行参数拒绝，按现有 transport 证明、零消费事实和资源 owner 结算释放预留；扩充的用途必须匹配自己的可信错误码和原调用。未知、网络中断和无用量不作为零消费证明，不修补前轮无证明的旧预留。
- 模型决定只选已冻结可用集合中的动作。创作仍在当前个人身份下执行，第 2.3 节的脚本与提示输入保持不可信数据，不开放任意工具、外部写入或由模型自动保存。用户可以在草稿中纠正模型的理解；信息不确定时以补充对话处理，不把模型推测声明为已核实业务事实。

#### 验证、范围和停止点

本轮验证只覆盖两种实际入口：不选择技能一次发送生成标题草稿，以及手选准确版本后一次发送生成。两者都应无「进入技能创作」、第二份需求输入或额外生成按钮；允许原模型准备进度与失败重试。

TDD 覆盖闭合意图与可用集合、主动选择优先、原始文本/快照绑定、同键异载荷、同一父命令并发只绑定一次、期限内与期限外交接、相同会话两个独立消息的隔离、首次创建/发送响应丢失、切换会员、无权限、未配置、明确拒绝零消费及未知恢复；复用现有 PostgreSQL 与模型/商业 owner 测试，不建设新验收平台。浏览器使用受控回执验证单输入、一次发送、对话草稿、手工编辑/保存、技能撤销和双标签恢复。真实模型沿现有隔离环境按授权验证并与用量明细核对，保留实例只在准确候选和当前授权下更新。独立检查不是用户产品验收。

现有商品内容、项目和原手动关联不扩范围。旧未决请求只履行原已确认操作；没有“为了兼容旧页面”建立 wrapper、fallback 或第二事实源。

部署先由原 schema owner 安装有界字段及权限，再准备新用途配置和新后端，最后更新前端；对外开放前核对准确提示/格式、权限与只读回执。准备期间既有店铺识别用途和其他已开放模块保持。新消息尚未获准接纳前可切回旧镜像；一旦接纳了新格式消息，不以旧 reader 覆盖新格式事实。故障时保留新 reader 与原请求恢复，暂停新发送并用范围内前向修复，不删除关系字段、回执或用户草稿。此限制只针对本轮新增事实，不要求全量环境演练。

### 2.5 主动选择已有 Agent 技能（2026-11-18 当前增量）

Design Basis: Reuse Existing Architecture · Ready。用户明确要求技能库已有 Agent 技能也可主动选择。复用本稿第2.2/8.1节、[原商品入口](domains/ai/official-skill-product-entry.md)、[技能准入](skill-capability.md)和原图片执行合同。Skill唯一持有准确版本及准入；Collection、标题和图片各自保留原事实、确认、幂等、恢复和结算。不增加表、业务状态机、权限、收费或模型执行语义。

右侧抽屉沿用技能库的「官方模板 / 我的技能 / 团队技能」分类，默认全部；分类只筛选原候选并保留名称搜索，不建立新分类事实。右侧抽屉同时读取原创作候选、标题candidates和image-candidates，按标题、图片、技能创作展示名称、来源、用途和版本，支持查找、独立重试和空状态。标题含原候选允许的官方/本人/团队版本，图片含原候选允许的官方/团队版本；未启用或未准入技能不伪装为可执行。某类读取失败不隐藏其他类。账号、企业或权限变化使旧选择和迟到读取失效。

已有技能选定后显示名称、来源、版本及前往原处理页的操作。选择仅为本次使用准备，Chat草稿保留；不将已有标题或图片技能误发给创建技能或需求识别模型。标题进入原商品选择和标题确认，固定Chat选定的ID/版本/摘要；取消或更换返回Chat，不静默降级或换最新版。图片进入原商品选择、显式单件转入及原图确认；原图片权限、报价、原请求与人工采用保持。普通官方模板入口仍仅接受官方候选，Chat导航按同一当前candidates核对获准来源；URL不授予权限。

返回地址只接受当前Chat的新建或会话站内路径（可保留合法项目/店铺入口参数），导航绑定原user/org/target和精确技能。待用选择按原账号/企业/入口在同标签页保留；标题提交前将原恢复URL记为导航位置，原请求及回执仍归原标题owner。沿原Chat重开时优先核实原标题请求，候选失效只影响新确认，不阻止原请求按原披露权限读取。浏览器无法保留原恢复位置时不发送新标题请求。项目改绑的新会话不带入旧技能选择或请求。

验证覆盖各来源候选、独立失败重试、准确引用与无模型副作用、标题确认锁定、原请求恢复、scope切换和迟到响应、返回草稿、窄屏与键盘，以及创建技能原路径回归。实现完成后独立最终交付复核，实际模型调用及用户验收单独报告。

### 2.6 统一技能创作入口

用户要求抽屉仅保留「创建技能」。直接描述个人商品标题技能，或选中「创建技能」后在同一 Chat 输入框描述，均可生成原标题草稿。创作按钮只设置输入区用途，发送才授权本次处理。已有标题、图片和文字技能的选择及使用仍沿原流程。采用 Independent Architecture 的有界补充。

AI Workbench 持有本次消息、冻结的 `creatorOnly` 选择和原请求。Skill owner 继续提供当前可用的原标题创作准确版本，治理路由继续用已获准的意图模型、原输出协议及资费。直接消息和既有版本选择保留原意图提示、输入摘要、原键与结果。`creatorOnly` 只用于尚未指定产物类型的创作消息，与准确版本选择或修订互斥。它与原文本一同冻结到现有结构、指纹及模型输入，已有请求缺省行为保持。服务器只允许原标题创作或澄清结果，派发结果和恢复回执均校验同一冻结范围。提示使用有界静态规则，用户原文作为数据。不会通过关键词判断自由文本，也不接受模型选择版本、身份或参数。

标题意图明确时复用原子绑定和已批准的标题草稿、可选 Python、编辑、保存和恢复。若未确认标题用途，在当前 Chat 保留原需求并说明可补充标题规则。已开放通用文字创作的实例也可在此继续为文字技能，使用现 #1431 准入和已有创作卡片，带入当前输入，只有再次明确生成才调用原通用文字模型。不会把模型的澄清当作授权，也不会在失败、未确认或切换企业时自动开始文字创作。模型不可用时保留原输入及错误反馈；既有显式版本请求继续沿冻结用途处理。企业/成员、用量计价、发布和执行权限、幂等边界和表结构保持原合同。

验证直接与选择后发送、范围约束、原结算和未知请求、三种旧输入（普通、精确版本、精确修订）的原字节行为、通用文字草稿的明确继续、切换会话，以及抽屉分类和现有原请求回归。只按已授权的 CI 候选更新保留实例。

## 3. 创建项目

新项目从项目中心的现有创建流程进入，Chat 不再提供新的创建入口。项目字段、权限、关联店铺与回执继续由项目中心负责。

已有 Chat 创建项目请求保持原有恢复合同：在原账号、企业和入口读取已保存的原键与完整字段，仅由「核对原创建项目请求」核对；加载记录不自动提交。结果未知或失败时继续保留原记录，重复核对沿同一请求。收到项目回执后保留「项目已创建 / 查看项目」，用户可返回原项目详情或继续聊天。移除选择入口不移除原请求、会话和项目，也不改变项目管理权限或模型依赖。

## 4. 从已有项目执行一项任务

1. **确定项目。** 从项目中心进入项目会话，或打开已有项目会话，复用工作范围候选读取核对同一企业内本人可用的未归档项目。以服务端按当前权限返回的项目范围为准，只有当前会话可继续发送，且它固定的项目 ID、绑定店铺 ID 都与预览一致时，才在原会话继续。当前会话为通用、单店或另一项目时，点击「在所选项目的对话中继续」，走现有按项目新建会话入口。同一项目的店铺换绑、增加或解除时，也按下文规则开新会话。
2. **准备一项商品内容任务。** 选一件有权限的自有商品或已保存的源商品，选择目标语言和处理字段，按原内容任务的表单填写需求。卡片分别呈现「项目关联店铺」和「本次任务店铺」。两者不同时，如果当前商品内容路径无法在规划、确认、启动和结果中准确使用本次目标，就在生成方案前阻止该组合并保留输入。首版按已有证据开放匹配的店铺组合。用户主动清除本次选择后，卡片明示「未选择本次店铺」，仅在现有任务路径允许时继续。执行时仍须核对项目关联店铺的原有依赖。
3. **点击「生成方案」。** 用户进入所选项目的会话并核对信息后，点击「生成方案」才沿已有消息与规划路径提交选定项目、店铺、商品及处理内容。开启会话与带入草稿只准备输入。规划可能消耗点数，按钮前明示。可准确取得的估算或上限来自现有计价信息。只有收到可执行提案才显示待确认卡。卡片列出项目、本次店铺、商品名称或可核对的商品链接、语言、字段、结果处理方式及原执行限制和可用预算信息。
4. **点击「确认并创建任务」。** 用户可以先返回修改。尚未提交的修改清除本页原卡片的确认入口，用户重新生成方案。服务端沿原确认合同重新校验方案归属与时效、企业及资源权限、所用项目和店铺、商品版本及执行条件。项目状态、输入或执行条件变化使原方案不可用时，提示重新核对并生成方案。确认成功得到一个 BusinessTask，并按原路径尝试启动。返回卡显示「任务已提交」和「查看任务」，实际启动、待审核、采用和结果状态由任务详情展示。任务已保存但启动仍未确认时，保留同一个任务，并走原任务的启动或核实入口。

已确认任务保留当时的项目范围与本次请求信息。项目后来归档不会自动取消已有任务，后续读取与执行效果仍分别检查当前权限。任务完成后的审核与采用沿商品内容原流程。

### 4.1 同一项目改绑店铺后的继续方式

1. **提示用户开启新会话。** 如果项目原关联 A 店、现在关联 B 店，显示「项目关联店铺已变更，请在新对话中继续」。只显示当前仍有权读取的店铺信息。用户核对项目和当前绑定后点击「在新对话中继续」，沿现有项目范围预览与确认创建新会话。服务端核对预览与实际绑定。当前项目范围读取失败时，保留草稿并提供重新核对入口。
2. **带入草稿，重新选择本次店铺。** 沿原 Chat 草稿交接约定，在当前浏览器标签页把同一用户、同一企业下尚未提交的需求带到新会话的输入框。目标会话已有草稿、用户输入或未决请求时，保留两边内容，让用户核对。新会话分别显示「项目关联店铺」和「本次任务店铺」。本次任务店铺由用户重新确认，按原规则核对访问权限、连接状态及与当前任务的匹配。打开新会话和带入草稿均不触发规划或扣点。
3. **在原范围核实历史和未决操作。** 旧会话仍保留固定范围，历史按原依赖和当前权限读取。已发送的消息、已有方案或任务和未决请求留在原会话。若变更在预览之后、创建会话、提交规划或确认方案时才被发现，沿原请求键、载荷和范围先核实该操作。已有回执就展示当前权限允许看到的原结果，结果仍不明就保留原核实入口和原有操作锁。原操作明确未受理，或已得到终态后，用户才能在最新授权范围下明确发起新的继续操作。新会话使用自己的创建和发送请求，旧请求及其输入不换键、不换店、不搬到新会话重发。

| AI Capability 与资源账本管理模型调用、预留与结算 | 经现有 governed 文本执行、企业路由和点数服务处理。 | 创作以登记用途复用原模型调用与计量，Chat 卡片读取对应报价和结果。 |

- **当前授权。** 浏览器选项、历史选择或粘贴链接仅作为输入。项目、店铺、商品和任务由各自 owner 按当前账号、企业及原资源权限校验。项目列表及任务关联不授予资源权限。权限变化后，原 owner 的读侧隐藏受限内容，写侧停止未获准的新效果。店铺背景的读取范围限于既有白名单。关联项目不会自动把关联资料、订单或流量送入模型。
- **事务与归属。** 项目保存、任务确认和项目关系写入分别使用原 owner 事务。关系保存准确的引用，任务的范围与执行输入来自原会话和已冻结的消息。创作增加第 2.1 节的专用命令、生成结果和待核实保存输入。已有项目、任务、技能、审核和计量事实继续从其原 owner 读取。
- **幂等与结果不明。** 创建项目、发送规划、确认任务、添加关联各沿对应原请求键与回执。相同键和相同输入核对原结果，相同键换输入按原合同拒绝。提交中禁用重复点击。响应中断时卡片显示「结果待确认」，用原键和原请求核实。任务已确认但启动结果不明时，仅核实原任务及原运行；规划或执行能否继续由原准入和恢复协议决定。刷新按既有同会话恢复能力还原，重试读取原结果时也要检查当前披露权限。
- **边界与实施准入。** 项目操作使用原项目和 Chat 接口，创作按第 2.1 节增加专用用途。各自沿现有分页、请求大小、时限及预算上限。项目路径继续验证店铺到执行的一致性、会话间草稿交接、创建项目与模型配置的独立性，以及任务提交和项目关联的边界。现有路径无法可靠表达的店铺组合须限制入口。设计评审与执行 Issue 的准入完成后，方可开工修改生产业务路径。

## 7. 验收方法

在有授权的现有试用环境中，从正常的 Chat 入口使用受控模型和合成业务数据验证。下表前四项验收「创建技能」首批功能。现有标题技能交接在后续开放时验收，项目路径验收移除新入口后原会话与原请求仍可继续。真实模型使用和用户试用记录按实际执行区分。以下是验收预期，当前均为 `NOT_RUN`。

| 验收项 | 操作与通过条件 |
| --- | --- |
| 选择并创建个人标题技能 | 在 Chat 选店旁打开右侧抽屉，选择官方「创建技能」准确版本，填写需求并确认生成。核对返回的是一份可编辑的标题技能文字草稿，生成后「我的技能」尚无新记录。人工修改并检查，确认保存后得到一条可从「我的技能」打开的 v1 私有草稿，内容为最终确认版本。点取消、反复检查格式或刷新读取原草稿皆不生成新的技能版本。 |
| 创作隔离与输出边界 | 覆盖官方创作版本停用、无企业授权、切换企业或账号、迟到响应、篡改用途和越权引用。新企业看不到旧生成或待核实保存。模型只读取本次显式输入和官方材料，且无法发起保存、脚本或网络操作。把创作技能填入原标题或图片入口应被拒绝，输出和保存只接受合规的单份文字标题技能。 |
| 创作计费和生成恢复 | 覆盖报价失效、额度不足、双击、同键异输入、模型未发送、已计量但输出无效、模型已回应但点数结算失败、已认领后超时、模型结果与草稿之间提交丢失。核对确认前无预留或调用，同一生成键至多一次发送，已确认使用按原规则记账，未明时展示待核实。刷新核实不会把已认领调用重发。 |
| 确认保存与原请求恢复 | 覆盖人工修改后格式检查失效、同一草稿两标签使用不同键并发确认和首个保存成功后的迟到提交、保存事务已完成而响应丢失、工作台只冻结保存输入后中断。在企业 B 或仅刷新页面时均不触发保存。重新获准进入企业 A 原会话，由用户点击「核实原保存」，相同内容返回同一回执，其他内容不能覆盖或多建技能。已保存草稿的后续编辑通过技能库创建新版本。核实保存不再次生成或扣生成点数。 |
| 技能抽屉和标题确认 | 从选店旁打开右侧抽屉，按当前权限核对官方、个人、团队的标题候选，覆盖个人未准入、团队未共享、空列表和读取失败。选 v2 并前往标题页，核对名称、同一版本、已保存商品与用户选定的目标语言。不同店铺背景下，商品仍按原企业与商品权限列出。确认前没有运行、扣点或业务任务，正常发送聊天消息和执行项目任务均不消费该技能。确认生成后核对原标题运行所用版本。返回原 Chat 时核对未提交的输入和重新验证后的选择。 |
| 技能版本失效 | 在企业 A 选 v2，进入商品选择前或打开标题确认后停用 v2、撤销准入或改变可用候选。再次读取后显示原选择状态，可返回重选。直接提交过时引用同样被原服务拒绝。即使 v3 可用，当前确认也必须使用同一技能 ID、版本和摘要。核对从 Chat 进入的确认没有取消勾选技能或顺手替换版本的入口，用户可回到 Chat 重选。 |
| 切换企业 | 企业 A 的抽屉读取仍在进行时切到 B，或带着 A 的 v2 和商品进入确认页后切到 B。A 的迟到响应、商品和技能选择不得进入 B 的界面或新提交。只读 B 当前候选，B 的生成须重新显式选择与确认。使用旧入口链接也须校验账号、企业和商品权限。 |
| 旧请求恢复与原版本 | 分别覆盖原标题提交结果未知和 Chat 原会话的创建、规划或确认结果未知。标题提交后用页面返回或浏览器返回回到 Chat，再打开同一标题操作，应进入原核实地址而非新的确认页。改变当前技能、店铺或企业后，经当前授权回到原入口，同一请求继续使用原键、原输入和原范围。标题请求保留原技能版本；即使该版本已移出当前候选，仍按原权限读取已存在回执，或保留待核实状态。原请求不得被覆盖、换版本、改绑或在新会话自动重发。涉及仍需新执行的步骤时，由原服务按当前权限和版本状态决定。 |
| Chat 项目入口与已有请求恢复 | 新建和已有会话不展示「项目操作」选择入口。存在已保存创建请求时，原账号、企业和入口可核对同一键及完整字段；加载不自动提交。结果不明后重试返回同一项目，成功回执与详情链接继续显示；模型未配置仍能核对，不产生模型调用或业务任务。 |
| 已有项目任务 | 从项目中心或已有项目会话进入，核对未归档项目和店铺，再选一件商品及至少一个可用的非标题字段。生成方案后核对对象、店铺、处理内容与费用说明。点击确认前没有已创建的业务任务；确认后得到唯一任务，可从 Chat 打开，并在任务中心按该项目找到。以实际任务详情核对启动或未启动状态和结果。 |
| 手动关联和读取 | 新任务尚未手动关联时，能按项目范围在任务中心找到，项目详情的「任务」页只显示其已关联记录。在项目详情粘贴本次任务链接并添加，刷新后出现准确的一条记录，点击回到原任务。重复添加不增加条目，移除后原任务仍可访问。 |
| 店铺与会话范围 | 从另一个项目的会话进入所选项目，核对需求交接和旧会话范围。对尚未支持的 A 店项目与 B 店操作组合，页面在生成方案前给出可修正提示，无模型发送或任务新建。改店或改任务内容后，原确认卡无法在当前界面继续提交。 |
| 同一项目改绑店铺 | 用项目 P 原关联 A 店的旧会话留一份未提交草稿，将 P 改绑到 B 店后再次打开执行卡。应提示进入新会话，并以 P 和 B 店范围打开新会话。核对草稿可编辑、待用户重新确认本次店铺，开启会话时无规划调用。用户选择 B 店并主动生成方案后，可沿原确认路径提交唯一任务。旧会话历史仍按 A 店的原范围及当前权限读取。再覆盖预览后发生改绑且原创建、规划或确认结果待核实的情形，原请求只在原范围核对，返回原回执或继续显示待核实，新会话没有自动补发。 |
| 权限和失效 | 使用无项目管理权限的成员验证创建及关联均不能成功，并按原授权验证已有项目读取与任务能力。尝试用他人或另一企业的项目或任务引用，预期不泄露记录。方案生成后归档项目、撤销相关权限或改动依赖，确认应拒绝过时方案并说明处理方式。 |
| 结果待确认与可用性 | 用现有受控方式覆盖提交结果丢失或重复点击。恢复原项目创建、任务确认或关联时，仍只产生对应的一条记录。窄屏和键盘下可完成选择、返回修改、确认、核对原请求和查看结果。 |

实现侧使用原项目中心、Chat、任务中心及商品内容的有针对性检查，覆盖各自改变的行为。独立验证者或用户按上述路径核对可操作结果。验收记录注明环境、执行范围和实际结果，区分受控验证、真实模型和用户试用。

### 隔离试用入口

全新隔离环境沿[工作台试用交接](../operations/ai-workbench-chat-trial.md#准备当前应用)初始化工作台库和受限运行角色，并通过技能库现有「安装官方技能」登记「创建技能」v2。在当前企业启用完整 Workbench，配置 `aiWorkbench.skillAuthoringTextPolicies` 及 `modelRoutePricing.bindings` 中对应的 `ai_workbench_skill_authoring` 文本用途，沿现有企业渠道绑定已准入的模型和价格。脚本草稿使用 `ai-workbench-skill-authoring-v2` 提示版本与 `personal-title-skill-draft-v2` 输出格式。文字首批继续识别 v1 的准确版本及原回执。服务启动只校验配置与可用性。

已有首批创作表时，数据库 owner 可通过 `ai-workbench-schema-init --skill-authoring-only --runtime-role ai_workbench_runtime` 增加有界列和授权。命令还要求填写 `--expected-database`、`--expected-server-address` 和 `--expected-server-port`，并沿原私有 `AI_WORKBENCH_SCHEMA_DSN` 连接。旧请求和待保存原文按原格式读回。应用不会自行改表。

正常登录隔离 Console 后，打开 `/workbench/ai/chat`，在选店旁打开「选择技能 → 创建技能」。输入与店铺无关的标题规则示例，直接点「生成草稿」。查看文字草稿或展开 Python 代码，按需编辑或点「生成修改」。自动格式检查通过后，点「保存到我的技能」确认。通过结果卡进入「我的技能」核对私有 v1，消耗在「用量明细」中查「创建技能」使用记录。结果待核实时，回原企业和会话选择「核实原生成请求」或「核实原保存」。

## 8. 设计复核记录

### 8.1 既有标题技能交接

### 8.3 「创建技能」脚本创作增量

2026-11-17 独立复核核对自动报价、付费确认、草稿修订与保存并发、原请求恢复和原标题脚本执行权限。产品范围和交互以第 2.3 节为准。

- `BLOCKER` 已关闭。若另一个标签已经保存或推进修订，过时修改可能发起无法应用的付费调用。现在修改确认和最终派发均与同一草稿根的保存及修订串行核对。先取得派发准入的请求按实际用量和原回执处理，迟到结果不能覆盖草稿或已确认保存。
- `IMPLEMENTATION_TEST`。验证自动报价没有逐次持久记录，核对确认事务与报价过期的并发、首响应丢失、显式格式版本和原待保存包重放。

### 当前增量 · OpenAI 参数拒绝的零消费结算

Design Basis 为 Independent Architecture 的有界补充，沿第 2.3 节和原模型、点数 owner。用户要求修复 PR #1400 在隔离环境实测中遇到的明确参数拒绝仍占用点数。当前案例是 Chat「创建技能」选择 OpenAI 直连 GPT-5.4 Mini，发送旧的 `max_tokens` 参数后收到 HTTP 400。超时、断线、响应缺损、网关拒绝、限流、历史调用与其他 provider/业务均沿原结果不明与有用量的结算规则。参考 [OpenAI Chat Completions 参数](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) 和 [OpenAI 错误说明](https://developers.openai.com/api/docs/guides/error-codes)。

- 仅原 governed transport 在该原调用的唯一一次网络交接后接收的明确预执行参数校验拒绝可以提出零消费事实。要求已准入的 `openai`／`openai-direct`／`gpt-5.4-mini-2026-03-17`，实际发送到 `https://api.openai.com/v1/chat/completions`，出站 JSON 含 `max_tokens`，响应为 HTTP 400 和有界、完整、无重复键的 JSON 错误对象，准确 `type=invalid_request_error, code=unsupported_parameter, param=max_tokens`，含单一有效请求标识，响应不能同时含用量或生成结果。类型和字段比较采用有限协议规则，不解释自由文本。OpenAI 参数文档描述旧参数和替代参数，仅与本次真实直连拒绝和原发送记录共同支持预执行判定。
- 原 Executor 持有发送来源，生成终态前再次限定「创建技能」用途。原 AI Invocation owner 持久化 `failed`、`provider_rejected`、固定版本的拒绝码、请求标识摘要及原结束时刻。保持 `UsageKnown=false` 且明确本系统费用为零，不从无用量推断。商业 owner 读原终态、验证该固定策略适用、复用已派发零消费结算，原预留和原成员月限只释放一次。使用已有字段、原原子账本和原 RecoverDue，无 schema、新 owner、附加账本或历史回填。
- 复用原固定派发、点数预留和所属范围校验。拒绝回执仅在原调用结束后写入，旧的 dispatched/UNKNOWN 不会被从日志翻译为新证明。账本以原 reserve fingerprint、原成员与原 finalize operation 的证明结算。成功、输出已观察但验证失败、余额不足、结果未知仍按原规则处理。原键核实只读，不会重新发送。调用终态或账本回执未确认时仍待核实。原账本确认零消费后，Chat 显示生成失败并可由用户主动发起新请求。
- 验证严格证据变体、未知与有用量的原行为、最终回执前后的失败状态和同键不重发。隔离环境先用同一真实模型的参数拒绝复现账本原预留全额释放及实际扣除为零，再用正确模型适配生成并保存技能、执行一次原标题处理，核对「用量明细」与实际扣除。保持 35444 现状。

- 原调用已记录该精确拒绝且商业回执尚未确认时，在原生成键下保持待核实。若原生成已进入 UNKNOWN，后来原调用与原零消费回执才齐备，允许当前账号、企业、会话、会员按同一生成键和调用标识把 READY/UNKNOWN 收敛为 FAILED。该投影只能由原账本回执确认，不能重发、改写已生成草稿或影响任何其他 UNKNOWN。Chat 保留查看和核实未明生成或修订的入口，刷新后仍按同一原键查询。

独立复核结论为 IMPLEMENTATION_READY。复核确认原调用与商业结算先后可恢复、原 UNKNOWN 迟到收敛、自动拒绝策略与 #1165 人工恢复分别受限。准确拒绝元组和实际预留返还留隔离验证。
