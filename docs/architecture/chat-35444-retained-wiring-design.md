## 当前事实和事实 owner

- 只读检查显示原前后端健康；原 Chat `commands` 目前为 `COMPLETE=1`，计划 `CLOSED=2`、发生项 `RECONCILED=2`。此为查询时刻快照，并非维护窗口无在途证明。
- Chat 的 `messages` 新增 `message_kind`、`store_query_status`，`commands` 新增 `route_commit_deadline`、`route_result`；仅替换受影响的三项命令 CHECK，按目标 schema 增加消息类型、引用和 route_result 约束。旧普通消息默认投影为 `TEXT`，不改变旧消息内容或既有命令语义。唯一授权增量为 `ai_workbench_runtime` 对 `commands.route_result` 的列级 UPDATE；不得授表级 UPDATE、其他列 UPDATE、DELETE、DDL 或改变其他角色。
- 当前业务 PostgreSQL 为既有独立业务集群，目标为其中 `product_agent`，schema owner `product_agent_owner`，服务角色 `ai_workbench_runtime`。ZITADEL 身份数据库是另一 PostgreSQL 实例，身份归 ZITADEL；商品和已批准资产的数据库事实分别归现有 Product/Asset owner，图片对象归各现有对象存储 owner；Temporal 历史和调度仍归现有 Temporal/任务 owner。Chat 入口不持有这些事实，也不创建第二事实源。
- 当前只读容器清单表明身份 DB 使用 `task-processor-unified-20261010-identity-db` 卷与独立身份密钥卷；本地图片至少有 `source-media-objects`、`image799-objects` 两个对象卷及各自密钥卷；当前 Temporal 使用 `task-processor-unified-20261010-data-services-temporal` 中的 `/data/temporal.db`。这些只是运行时观察，图片引用、其他对象/凭据卷和活跃队列须在维护前由其 owner 完整盘点，不得假设这份列表穷尽所有依赖。

## 合同 → 实现 → 注入 → 消费者

设计一个**显式人工调用的、有界保留目标 owner 维护入口**，与普通服务启动及空库初始化分离。输入是受限本机维护清单：精确环境身份、目标/旧版本/目标版本、预期数据库 system identifier 与 OID、允许的角色/owner 和批准的差异基线、已验证备份清单及维护窗口身份。清单不包含明文密钥，连接凭据只从现有私密入口获取。输出仅为非敏感的目标指纹、前/后状态、差异检查和结果；不记录密钥或商品内容。`inspect` 为只读；写入须显式区分并在未来单独获准。

设计上维护入口调用原 `aiworkbench` schema/权限 owner 的精确合同，不由 UI、服务启动、Compose 或模型路径触发。原 runtime 启动继续验证目标 schema/窄授权，只有通过后才注入现有 Chat/Store 消费者；原企业、成员、项目、店铺上下文重新授权，历史会话不能保留已撤权店铺统计。实现需复用现有 schema 定义和安装/验证能力；没有批准前不引入双读、回退 adapter、平行库或第二 owner。

## 目标与权限校验

维护窗口外只读 `inspect` 核对当前运行容器/项目、实际实例与目标数据库、原私密 manifest 中连接目标、数据库 system identifier/OID、schema 与表 owner、受限角色和主线/原镜像身份。窗口内冻结相关应用及 worker，排除其他写入者，再次核对以上身份；对象/角色管理员的其他变更也须被同一维护窗口明确排除。PostgreSQL 的业务表锁不能阻止超级用户或其他会话修改集群角色，不能声称表锁提供这一保证；无法确保管理员变更冻结时停止。

由现有获准维护连接在**同一数据库会话、同一事务**验证真实 PostgreSQL 身份、数据库及 owner、旧列/类型/默认值、全部相关约束的定义及有效性、owner/角色属性和成员关系、schema/表/列的实际有效授权与继承授权。身份需要特权读取时，沿现有集群管理员的私密维护能力只用于核验；事务内先核对真实 `session_user`/目标，再以 `SET LOCAL ROLE product_agent_owner` 执行 DDL，服务始终使用独立受限 runtime。若既有权限无法安全完成校验则拒绝，不给 serving 增加读取、DDL 或管理员权限。

对相关工作台表取排他锁并设置有界锁/语句超时；锁内重查目标与数据库目录指纹、表结构、约束和本域在途命令。按固定旧/新 schema 合同做精确差异，不按约束名盲删；确保旧行满足目标约束，仅完成四列、精确约束与上述列授权，在同一事务提交。事务前后的既有行、不可变事实和不相关 ACL 要可核对；检查异常立即整体回滚，不自动修复漂移。跨数据库和集群管理员变更依靠维护窗口排除、各 owner 对账，不伪装为跨库原子事务。

## 在途、重试与结果不明

维护前由各 owner 核对 Chat commands、任务动作回执、计划/发生项，以及已配置的 Agent、商业计费和 Temporal 中与本次路径相关的在途/UNKNOWN；冻结后再次有界核实，并在整个窗口保持冻结。**工作台表锁内只核查同库 Chat 事实**，不持锁等待其他 owner 或把跨库状态伪装成事务快照；任一其他 owner 的冻结或核对失效均停止。不得以单个枚举的已知状态集合代替现行合同。`READY_TO_DISPATCH`、`PLANNER_UNKNOWN`、被占用/未知动作、正在运行或结果未核实的相关调度均阻止更新；新的未知状态按未决处理。保留原请求键、deadline、回执和账本，不换键、不重发模型、不伪造终态。

既有 15.445282 点预留是**已识别的原账本保留事实**，不是本次要释放或重试的对象。核实其绑定、状态与账本一致，确认没有相关正在执行的恢复/调用；若仍有未判定 provider 结果就保留原状态，不能把它当成已结算，也不因其存在擅自改变计费。若不能确认没有在途副作用或无法保全该事实，停止维护。

每次写入只允许对明确指纹执行一次：旧态完整匹配可施行；已是目标态须完整核对结构、约束、有效 ACL 和旧事实后报告 `ALREADY_READY`，不得重复改写；混合态或漂移返回拒绝。并发请求在同一事务锁下只有一个完成，后到者识别完整目标态或拒绝。提交 ACK 丢失时不把异常当作回滚：保留相同目标和操作身份，停止自动重试，通过**同目标只读检查**分类为完整旧态、完整目标态或混合/未知；仅前两者能按对应既有程序继续，后者停写人工处理。不新建持久恢复表或另一个操作事实 owner。
