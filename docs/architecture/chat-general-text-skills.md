# 硕米 Chat 创建并使用个人文字技能

> Design Basis 为 Independent Architecture。独立架构复核确认达到 `IMPLEMENTATION_READY`。
> 2026-11-18 用户决定，本轮开放通用创作，保存后可以在硕米 Chat 选择技能完成一次文字任务。已有商品标题技能能力由原消费者继续提供。
> 执行 Issue [#1429](https://github.com/henryxu1008/shuomi-ai-commerce/issues/1429)。

## 用户路径

用户在硕米 Chat 的「选择技能」抽屉选择「创建技能」，输入用途、处理规则与必要的样例。例如「把我给的交接笔记整理成待办表，缺负责人时标记待确认」。默认创建「在 Chat 中使用」的个人文字技能。明确要创建用于商品标题处理的技能时，用户可在同一卡片选择「处理商品标题」，走现有文字或 Python 标题草稿流程。

复用现有创作卡片的生成、修改、编辑、格式检查和保存。草稿展示可编辑的名称、用途和规则，从一段需求生成可用草稿。遇到会改变实际输出的未决规则，展示给用户确认。保存确认按钮说明个人可见、可在 Chat 选用。保存成功后显示「在 Chat 中使用」，回到同一消息输入区，并选中刚保存的准确版本。用户填写待处理文本后主动点发送，回复出现在会话中。之后可从同一抽屉重新选择。当前选择只用于本次发送。关闭抽屉回到输入区，失败保留原输入。窄屏使用现有抽屉与换行布局。

通用技能处理用户本次提供的文本。回复可能是文案、摘要、表格或待补信息。技能无法取得店铺、商品、项目、知识库或历史会话内容，无法执行脚本、工具、外部访问或创建业务提案。团队创作、共享授权、自动选择和外部平台写入不在本轮范围。技能格式以 [Agent Skills 规范](https://agentskills.io/specification) 的 `name`、`description` 与 Markdown 正文为核心。硕米在规范允许的 `metadata` 中记录用途和显示名称，沿已有 Skill 内容查看方式读取原始 `SKILL.md`。

## 设计依据与事实 owner

- [现有创作和保存](chat-project-actions.md)及 [PR #1400](https://github.com/henryxu1008/shuomi-ai-commerce/pull/1400) 提供候选基线。该 PR 当前尚未合并。本增量依赖其创作、保存和恢复能力，保持独立实施和评审，合并候选须包含已合入的前置能力。
- [Skill](skill-capability.md) 是技能、归属、版本、包摘要、可用状态与保存回执的 owner。现有 `Package.Supports` 把无用途标记的包当作商品标题。新能力使用明确的 `chat-text` 用途，避免通用包误入商品入口；不修改无标记包既有解释。普通用途标签本身不赋予任何使用权。Legacy decision 为 EXTRACT，复用已存在的 Skill 库、创作与 Chat。
- [AI Workbench](ai-workbench-chat-business-task.md) 持有会话、生成和发送命令、文本回复与引用。复用现有命令的占位、单次派发、无提案终结和回执，按冻结的文字技能引用区分用户看到的文字回复。不存在额外的技能任务账本。
- [AI Capability](ai-capability-platform.md) 和原商业 owner 继续负责模型路由、报价、限额、预留、发送及结算。保留现 `skill_authoring` 与 `chat_planning` 各自路由和完整 profile。文字使用的模型输出按下文文本合同处理，商品规划输出包络仍由其原消费者校验。由宿主冻结用途及消费提示合同 ID，绑定实际 system/prompt 和 `InputHash`，在预备及派发时使用同一受信模板。模型 profile 继续由 AI owner 解析和复核。准备及保存无模型调用，用户点发送授权本次调用。缺额度或配置时返回相应用户状态。

## 创作与个人保存

1. 官方创作沿同一发布 ID 加入 v3。通用文字选择绑定 v3，商品标题选择绑定已有 v2。沿 Skill owner 的官方安装命令支持原 v2 已安装实例追加 v3，以及新实例直接准备现行发布。保持既有 v1/v2 字节、摘要和历史可用状态，按已有官方发布、启用权限开放 v3。官方资源版本与 `format_version` 分别记录，v3 使用现 FormatVersion 2 的序列化输出形态。通用分支只接受 `name`、`displayName`、`description`、`instructions`，由服务端写出一个文字 `SKILL.md` 并复用 `ValidatePackage`。通用模式拒绝脚本、执行描述和额外文件。用途由冻结的显式选择决定，生成模型与保存请求均不能替换。
2. Workbench 继续按原账号、企业、成员、会话、当前修订锁和准确创作版本保存完整包及原保存意图。通用保存使用 Skill owner 的有界个人文字技能创建命令，在原 Skill 事务内一次保存为本人私有、Chat 可用的准确版本并写原回执。仅 `USER + PRIVATE + chat-text + 单一文字文件` 可由此命令创建为可用。界面明确「保存并在 Chat 启用」，此动作不在企业、团队或商品入口增加授权。标题草稿沿原可用状态流程。
3. 通用创作采用显式新增用途/提示合同版本。用途由严格匹配的官方创作版本和摘要确定，绑定预览确认 MAC、输入哈希、根草稿、修订及唯一保存意图，创建、修订和保存均使用已冻结用途。原 v1/v2 标题生成、修订、保存仍按原合同版本、原键、原包和回执核实。刷新因原键返回同一保存意图；相同键不同用途或内容返回冲突；迟到结果不能覆盖已冻结的保存或已推进的修订。

## 使用与单次发送

1. Chat 抽屉复用个人技能目录，只列当前验证账号持有、私有且已启用的当前文字版本。另存新版本后，启用当前版本才能从抽屉选用。目录只返回名称、用途、版本引用等元数据。选用由用户显式触发。服务端由 Skill owner 根据 ID、版本和摘要读取并核实实际归属，不采信浏览器提供的 owner、规则正文或授权。
2. 工作台以现 Chat 使用权限、有效企业及成员身份、现 Chat 模型为调用前置。复用有范围 Chat 已支持的 `scopeSelection.kind=general` 预览、确认与创建。保留前置工作背景的原授权及会员绑定，仅普通会话可发送。选用文字技能时，现输入区将请求发到 `/messages`，把技能选择、文本和路由一并绑定现有待恢复的消息请求，抢先于 `/intent` 分流。服务端 `Admission` 和 `Decide` 由准确文字消费合同分流，保留 Chat 与会话授权，再直接到 ChatPlan 路由，不进入标题/商品就绪、`TaskSelection` 和标题发送复验。已存在项目、店铺、商品选择或未决的其他发送时，给出返回原请求或打开普通对话的操作。选择不继承到新消息或其他会话，切账号或企业清除选择与晚到结果。
3. 在原消息命令的 `WorkScope` 保存可选的准确文字技能版本引用，并纳入同键请求指纹。普通消息无该字段时保持原字节语义。文字消费合同 ID 纳入模型输入哈希，派发重算必须一致。预备期先完成原会话归属及会员核对并向 Skill owner 读取有界内容，纯 `PlanPreparer` 仅计算确定性输入。派发复用 governed executor 的最终发送检查，核对账号、企业、命令会员、会话会员，持 Skill owner 的共享锁重新读取准确版本并比对输入哈希，直到现受控调用完成派发保证；回执阶段按原 Workbench 规则重新核对。模型仅看到本次消息与所选包正文，两者与宿主指令分开。直接取冻结命令的当次用户消息，禁止把历史窗口中的其他消息放进提示。
4. 新文字使用仅请求有界 UTF-8 文字或 Markdown。模型答复只作为消息内容，由程序固定生成无提案的 CLARIFY 终态，任何 JSON、商品规划字段或 Markdown 都不构成结构化命令。文字为空、超限、不完整或传输回复含工具时沿既有受控调用失败语义拒绝。包装完整 Markdown 的外层标记可去除，保留有意义的代码和表格正文。使用现有会话消息存储和安全 Markdown 展示。商品规划继续使用原严格对象校验。原完成事务仍锁住命令后核对文字技能引用与无提案结果。恢复只核实原调用，保持用量确认和原键语义。
   - 试用证据证明仅兼容 JSON 围栏仍会拒绝已正常完成的模型响应，核心首次发送可能无法取得结果。此前解释为非提案业务 JSON 的外部格式，在本轮仅对新文字调用改为文本。新准备冻结文本合同 v2 的提示和 InputHash；已有未终结命令仅当原有记录的 InputHash 精确匹配时按 v1 恢复原请求，旧结果正常展示。一次调用只选用一个已冻结的合同，不额外派发或重写任何旧命令。
5. 原同键回执保留优先级。新请求使用被停用、撤销或更换摘要的版本时，拒绝派发并给出「技能已不可用，请重新选择」。冻结后派发前撤权触发原明确未发送路径；发送已开始时沿原受控调用和授权回执终结，保留原计量结论。对未知结果只核实原请求，禁止换版本、改无技能或再次发送。消息读回保留现 Chat 会员和会话权限，只凭同会话准确 assistant message ID 所属的已完成文字命令识别此次回复。不经商品历史路径重新推导此回复，不放宽其他消息的商品可见性。来源版本直接取原命令引用，不用该引用重新读取技能正文。技能版本、权限或会员切换不导致重复调用或另存第二份技能。

## 实施与验证

接线顺序为 Skill 包及个人保存/使用合同 → Workbench 创作与 Chat 消费 → governed text 输入及文字输出 → 当前 Chat 抽屉、创作卡和消息。已有 Skill 事务、会话结果事务及计量回执各持自己的事实。使用当前 `work_scope` JSON 和既有无提案终态。创作的用途字段使用有界增量，旧标题请求按已冻结 profile、版本和原包恢复，不做历史数据回填。

上线前须确认所有直接解析 Skill 包的服务（包括标题消费者与后台）及可选回退版本已识别并排除 `chat-text`。旧解析器会把未知用途读成未标记、再当作标题技能，所以在存在已保存通用包的环境中，#1400 二进制不属于安全回退候选。发布先升级并核对读取者，再由有权维护官方技能的账号使用原官方安装入口追加 v3。自动准备保留已安装版本，不能给已有 v2 的实例原地开启 v3。必要回退使用具备该识别能力的二进制或在现版本停用官方 v3 以关闭新的文字生成及发送。回退版本保持已有回复读回、拒绝新的文字发送，不把在途文字命令送入标题路径。现企业启用个人标题技能时，组合验证必须覆盖对已保存通用包的候选及直接引用均拒绝。用户数据不作为回退清除手段。

- 使用合成文字完成「创作 → 编辑 → 保存 → 选用 → 发送 → 回复」，核对一次生成和一次发送的用量类型、准确版本和重开会话可查看内容。标题与标题脚本原入口按现有定向检查复验。
- 验证明确可造成越权或重复调用的负例。外人、停用或撤销版本、标题及脚本包不可用于文字 Chat；变更版本、身份、企业或会员时拒绝新发送。生成和保存相同键多次只返回同一结果，不接受同键异内容。文字回复由程序禁止进入执行提案。
- 验证取消、刷新、已接收但响应丢失、未授权失败、上下文切换、键盘操作与窄屏主要路径。使用现有 Go、前端与受控回执浏览器检查，真实模型、保留实例更新与用户验收沿各自授权。

独立复核确认三个实施前阻塞已关闭。普通会话可以通过确切消息路由完成文字任务，官方 v3 的创作流程复用已批准的 model profile 和冻结回执，读取新包的标题路径及回退版本必须显式排除通用文字包。撤权与发送的时序、失败回执、计量和原 v2 标题回执纳入上述定向实现验证。
