执行 [#1485](https://github.com/henryxu1008/shuomi-ai-commerce/issues/1485)，关联 [#298](https://github.com/henryxu1008/shuomi-ai-commerce/issues/298)。Design Basis 为 Independent Architecture。Admission Status 为 **IMPLEMENTATION_READY**。2026-11-18 独立架构 Reviewer 已对多图稿和 `f6870af28` 接线核对，无剩余架构阻塞。多图线协议、整组容量和恢复作为实施验证；私有存储及合格模型路线是实际启用依赖。

## 用户结果与范围

依据用户于 2026-11-18 的最新决定「要支持多图」，同一条消息携带一组图片和文字问题。用户可多选文件、粘贴或拖入图片，发送前按加入顺序预览并逐张移除，发送后在同一会话按原顺序回看。用户可同时发商品正面、背面及铭牌，询问「铭牌上的型号是什么，跟包装上写的一样吗」。答复在需要核对时指出「图 1」「图 2」，看不清或证据不一致时提示用户核对。

首版默认每条消息 1–4 张 JPG/PNG，每张沿当前单图传输已有的 768 KiB、尺寸、像素及内容边界，整组原始文件合计不超过 2 MiB，并按模型配置检查整组上限。界面显示张数、预览和具体超限原因。开放给有普通 Chat 使用权限且企业具有合格多图路线和私有存储的成员。图片进入本条问答，与已经选中的技能冲突时用户可取消技能或移除图片。固定店铺或项目任务、技能配图、生成或编辑图片、跨消息重新读图、外链、商品保存及外部操作超出首版。

新建页可先附图填问题，沿[新会话先输入需求](chat-compose-before-create.md)创建普通会话并带入原草稿。在输入区点击「发送消息」才发生附件写入和模型调用。预览、移除、创建和历史读取均无模型调用。后续消息不隐式引用旧图片。复用现有输入区、主题和按钮，保持窄屏、键盘和纯文本粘贴可用。用量继续在「用量明细」查看。

运行配置在 `aiWorkbench.chatImageTextPolicies` 按已准入企业声明多图用途及其静态上限，并在 `modelRoutePricing.bindings` 为同一用途绑定合格的多模态路线、资费和单次用量上限。只有开启私有图片存储和容量计量的商品内容工作台才装配该用途；绑定可收窄原上限。

新增同一会话下的有界提交入口，只接收文字、一个有序图片数组及原消息键。BFF 复用同源鉴权，新增入口独立限制原图合计、整个编码请求大小及字段数量，原文字及技能请求上限保持。后端按实际字节逐图检查长度、类型、尺寸、像素和摘要。图片文件名、外链、object key 和模型身份不作为客户端输入。

## 模型及计量

- 适配器从冻结有序数组确定性构造一个文字 part 和 N 个图像 part，在实际网络派发前独立验证数量、顺序、每张类型和内容摘要、提示内容以及总 wire 大小。首版仅开放明确通过多图线协议、实际用量映射和回执测试的路线。当前只允许单图的渠道不会自动开放；原单图和纯文本操作的编码、指纹和预算保持原契约。
- 整组报价按确切模型、适配器及 detail 下每张输入的有证据上界，加上文字、响应和线协议预算。校验模型整组输入及资源上限，超出时在写入前停止。复用原派发账本的一次请求、一次按实结算。OpenAI 的 Chat Completions 支持在 content 中提供多张图，并按图片输入消耗 token；这是供应商线协议依据，仍须在本产品完成准入和验收。[Images and vision](https://developers.openai.com/api/docs/guides/images-vision?api-mode=chat)

## 持久化、权限和恢复

1. 本地预览与草稿不写服务端。用浏览器 IndexedDB 保存当前账号、企业、有效会员及入口/会话/草稿身份内的有序 Blob，现有标签页恢复记录只保留准确引用和原请求键。发送前在同一 IndexedDB 事务冻结完整 Blob 组、顺序、文字和请求身份，写入失败留住当前编辑并阻止提交。原消息接受后仍需留原待核实输入到终态，以支持同键调用恢复；终态或明确从未被存储/会话接受后进行对应本地状态的安全转换。切换身份时撤下原内容，回原身份先重验原会话和成员。
2. 复用 Service.Message 先回读原命令。首次请求在事务外重验 Chat 权限、有效会员、会话身份、实时可发送状态、普通范围、合格多图路线和整组预算。私有媒体或路线不可用则在对象写入前拒绝并保留图组。暂停新发送时，原合法已发图片和终态按当前原会话授权继续读。
3. 由企业、账号、会员、会话、请求键和原图序生成不可变私有对象名。容量操作指纹冻结原问题和有序图片标识。沿原容量 owner 一次预留整组字节/对象数，在一个绑定操作中绑定完整组，声明派发后按原组写入。每张读回验证后确认原对象计量，整组验证完毕后关闭作业；无部分模型调用。已确认对象不重复占用。同键改文字、换图或改顺序均冲突。途中出错保留该次原键，核对存储事实后续传明确未写对象；结果不明不释放预留或换键，不能凭当前无 Chat 回执推断原对象写入未发生。沿用原不可变条件写入，拒绝破坏已有对象；无新对象删除或孤儿清理策略。
4. 整组确认后纯 PlanPreparer 用同一个问题及有序图片计算 InputHash。原 Workbench T0 在同一事务落用户消息、整组引用和冻结模型配置；外部 I/O 不跨该事务。历史消息投影图片数量和顺序，二进制由同源会话、消息及索引的只读端点取得。服务重验租户、本人、有效会员、准确会话和命令，通过摘要/类型核验才以正确 MIME、Cache-Control private,no-store、nosniff 返回。存储路径、长期链接和原字节不出现在消息 JSON、数据库或日志中。归档和拒绝沿原会话授权。
5. 执行前重验原期限、身份、会话发送资格、全部图片字节与冻结模型。图片内文字和问题均作为数据，模型没有工具或可执行业务输出。完成事务固定只允许无提案文字终态，安全 Markdown 渲染复用现有 Chat。传输、拒绝、异常、超时和未知沿原计量与命令恢复。原请求用原键、原问题、原组和冻结模型核实，已存在的图片、命令或回执不按当前设置重做。只有有终态或能确定原存储和消息均未受理后，用户才可另发。

确认未接受原请求时，必须核对同一容量操作的原绑定/预留状态，与同键入场互斥，不能由当前路线不可用或一次数据库未发现会话回执直接推导。确认容量不足或模型预算不接受整组输入时，容量账本在同一企业入场锁内记录原操作的已中止回执，不占用预留，迟到的同键请求也不能上传。若模型预算变化之前原组已取得容量，沿原操作核实，不中止已接纳的写入。会话侧沿原序列化提交路径先核对原命令，仅在无接受回执时将上述证明交回界面恢复编辑。发现原组已获得容量或原消息已接受时沿原组核实。私有对象配置还须证明实际访问策略拒绝匿名读取；单独前缀或注册成功不能充当该证据。

Legacy decision 为 N/A。原纯文字或技能命令缺省图片字段时保持原序列化与指纹，不回填历史，不引入第二事实源。

## 验收

- 用至少两张不同的图片提问需要跨图核对的问题。覆盖新建及已有会话、多选/粘贴/拖入、逐张移除、单张/整组限制、文本粘贴、窄屏及刷新后按顺序回看。核对实际模型输入的顺序及每张字节，验证只调用一次。
- 验证整组容量不足、模型缺资格、撤权、前几张成功而后续图片失败、对象或 T0 回包丢失、多标签同键、同键换图或改顺序以及跨企业/会话/会员读取拒绝。重试从原组核对，任何部分不会提前进入模型。
- 隔离 PostgreSQL、私有对象替身和受控模型验证对象占用一次、用户消息和模型调用各一次，整组预算及实际用量正确记录，失败与未知沿原 owner。复用原单图用途的回归。真实供应商和 35444 接线需要对应授权并分别记录。
