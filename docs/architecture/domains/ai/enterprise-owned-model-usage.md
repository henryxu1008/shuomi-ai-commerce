# 企业自有渠道只记录用量

状态：2026-11-18 计费设计通过独立复核。用户已授权在 #1434 实施，并要求使用模拟厂商和隔离数据库验证。用户已明确企业自有渠道由企业直接向厂商付费，硕米只记录用量。平台渠道沿原规则扣点。本稿适用于 [#1432](https://github.com/henryxu1008/shuomi-ai-commerce/issues/1432) 首版已支持的企业文本用途。当前实现见 [#1434](https://github.com/henryxu1008/shuomi-ai-commerce/pull/1434)。合并、部署和付费测试暂缓。

## 产品规则

| 渠道 | 厂商费用 | 硕米在业务调用时的处理 |
| --- | --- | --- |
| 平台提供 | 平台的厂商账号承担厂商费用。 | 沿原参考价、汇率、估算上限、点数预留、成员点数限额和实际用量结算。从消费企业扣点。 |
| 企业自有 | 企业自己的厂商账号按厂商合同计费。 | 硕米记录可信用量和调用状态。无点数预留、扣减、释放、退款或补扣，无金额估算或点数报价。余额和成员 AI 点数限额不会阻止自有渠道调用。 |

保存 Key、关联型号、切换渠道照常只保存本地配置。现有官方模型资料查询仍是原只读功能，付费诊断继续搁置。

自有渠道仍须满足业务权限、企业和成员有效状态、实际用途准入、准确型号与协议、当前有效 Key，以及原请求长度、输入和输出用量上限、并发、次数、时限和单次发送约束。保留独立存在的非点数用量配额。原先只为点数预留和算费而设的参考价、汇率及金额上限只作用于平台渠道。对于只能用金额界限控制的新用途，不因移除扣点而放宽风险边界，须先具备原业务允许的独立用量约束。首版逐一核对实际已启用的共用文本用途。图片生成、图片分析、嵌入、搜索和后台任务本次沿各自既有合同。

## 受信分类和冻结

- 以目录中经批准的凭据所有权与来源为依据。#1434 正常登记的本企业自有渠道使用 `usage_only`，平台显式授权开放的渠道使用 `platform_points`。历史人工装配选项只有找到受信的既有自有归属事实才可按自有渠道接入已批准文本用途，归属不清的新增选项拒绝启用。现行部署绑定继续使用自己的批准合同，需纳入自有范围时须先核对原 Key 使用及付款主体。连接名、同型号、客户端参数或有效企业 ID 单独均不决定计费方式。
- 后端在候选、保存和运行使用同一资格目录。平台受信路径继续校验价目和汇率。自有路径按准确的模板／型号、非计费的用量解析合同和当前资格校验。自有候选及切换回读不依赖价目 owner 或汇率读取，不使用零费率或伪造价目模拟免扣。
- 在原 Invocation 中随业务身份、企业、用途、准确绑定、Key 版本和请求指纹冻结计费方式及必要的计量策略版本。平台路径继续冻结原价目和汇率。自有路径只冻结真实渠道／用量事实，不附虚构金额。发送前复核同一组合，计费方式或渠道资格自准备以来改变时拒绝旧准备发送，重新发起须用户按当前业务规则确认。
- 本规则从新版本正式启用后开始作用于新调用。已发送、已记录或已预留请求继续按其原发布版本和冻结事实收尾。历史缺字段的调用仅按原值和已存在的证据识别，不能因当前选用了自有渠道而回填为免扣。旧点数历史、待确认预留及 35444 试用数据保留原记录。追溯调整、退款和历史数据搬移需要独立决定。

## 实际代码接缝与事实归属

| 接缝 | 后续实现的职责 |
| --- | --- |
| 配置与运行资格 | 原 routeconfig 目录派生平台扣点或只记用量。SharedCatalog 目前共用价目、汇率和含费率的模型 profile。自有资格、报价准备和最后发送门禁须使用显式的按用量合同，保留非货币的模型规模约束。 |
| 发送前 | 原 Invocation 的唯一调用号仍先占位，按现有业务权限和并发门禁最多向原厂商发送一次。占位状态 `dispatched` 只表示领取了发送权，单靠它不能证明请求已交给厂商。当前 Executor 的 `ReserveAIInvocationUsage` 接到商业点数预留，自有分支不调用此端口。原端口内的 `AuthorizeModelInvocation` 负责按用途核对实时企业、成员与操作身份。自有路径在最后发送门禁复用此类业务核权，使用无点数副作用的授权端口，不因略过账本失去核权。逐个核对外层业务报价、企业余额、成员点数检查及多步任务预算，避免另一层仍为自有调用落点数。现有 `agent.Usage.Reserve/Settle` 依赖 `Quote.Known`、金额和币种，需有显式的用量模式及真实 Token 上限，继续使用原步骤、调用次数、总用量与时限，金额字段不适用。 |
| 完成与恢复 | Invocation 仍是原始用量和结果的唯一 owner。现有 `RecordInvocation` 与恢复会转商业结算，须依据原 Invocation 冻结的计费方式明确路由。商业 owner 的预留、结算及恢复入口也校验原调用模式，一律拒绝自有调用进入点数账务，即使有旧消费者误调。自有路径终态只写原调用，不接商业结算器、旧估算金额回退、provider 未收费证明和点数恢复工作器。重复处理同一事实无新增用量。原事实冲突拒绝覆盖。Chat 规划、店铺范围判断与内容等已接线用途都要按冻结方式验证业务收尾。店铺范围的 `VerifySettled`、`VerifyDecision`、`FailureState` 以及规划的 `FailureState` 对原扣点路径仍核对原账款或释放证明。自有路径只读原 Invocation 的企业／成员、原键、输入及结果摘要、真实用量和终态／未派发证据。不能依赖虚构的 `EstimatedCostKnown`、正用量或商业预留凭证。有效结构结果仍核对原业务输出。 |
| 展示与查询 | 「模型与服务」的自有项和确认框显示「企业自有 · 不消耗硕米 AI 点数」，说明费用由厂商向企业账号结算。平台项继续显示原参考点数口径。原「用量明细」增加独立读取的自有渠道用量区。现有明细由点数资源事件投影，自有调用没有该事件，需从现有 Invocation owner 读取去密事实。沿原商业明细和业务查看授权、实时企业和 `(企业, 用户, 成员)` 所属范围核对。列出时间、用途、渠道来源、型号、实际用量或「用量待核实」，按原调用号去重，以时间和调用号稳定分页。平台原点数流水原样显示。既有企业审计汇总用途和访问范围保持原合同。点数流水不为自有调用写零金额账单。自有请求的费用字段标为不适用，排除出硕米点数消耗、预留和金额估算的合计。厂商实际收款金额由企业看厂商账单。 |

当前核对点为[共享目录](../../../../internal/integration/aicapability/routeconfig/shared_catalog.go)、[调用准备与用量记录](../../../../internal/integration/aicapability/einomodel/executor.go)、[Invocation 持久化与恢复](../../../../internal/aicapability/store/gorm_invocation_recorder.go)、[商业点数适配器](../../../../internal/integration/orgresource/model_invocation_repository.go)、[用途与成员授权](../../../../internal/app/httpapi/product_agent_application.go)、[Chat 店铺范围收尾](../../../../internal/app/httpapi/ai_workbench_store_recovery.go)、[现有用量明细](../../../../internal/app/httpapi/commercial_resources.go)、[业务用量预算](../../../../internal/agent/budget.go)及[原已观察用量投影](../../../../internal/aicapability/store/observed_usage.go)。原投影只读已知且为正的用量事实，页面候选不得以它未返回一条记录推断零用量。自有调用的待核实与明确零用量用同一 Invocation owner 的受限投影呈现，不建第二账本。

## 持久化和启用顺序

- 在原 `ai_invocations` 表保存受约束、可空的计费方式字段。新路径显式存 `platform_points` 或 `usage_only`。历史空值只按旧冻结合同及合法历史证据识别，未知值或空值不可用来准备新的自有调用。不为旧记录填充值。对历史空值，保留 `modelPointFingerprint` 与 `InvocationBindingDigest` 的原版本和序列化形状，使已有预留、证明和回执可按原指纹校验。策略字段的加入不能改变旧指纹字节。
- 该字段随原唯一派发记录在可能发送前持久化，进入回执、原请求指纹和不可变字段比对。终态和原键核实必须留原方式。`ResolveDispatchedInvocation` 的自有恢复分支须从原行保留身份、绑定、用量策略和关联证据，不能走无适用价目的旧覆盖分支。持久化失败结果未知时，按原键确认，禁止换键重发。
- 当前 `VerifyModelPointInvocationSchema` 和 Run DB 权限检查是精确的列／访问门禁。后续实施从原 schema owner 的显式准备入口增加该字段，验证约束、原记录与非本改动的 ACL，更新原 runtime、账务事实读取、用量和恢复的有界列合同。部署必须先具备理解两种冻结记录的读取和恢复能力，再开放新自有调用，写入时失败关闭。暂停首版时保留能处理两种记录的代码与 schema，停用新增自有调用。禁用开关不产生点数回退。没有本稿授权旧程序读写新记录或删除字段回滚。[调用事实结构核验](../../../../internal/aicapability/store/model_point_fact.go)

## 结果及用量处理

| 场景 | 企业自有渠道 |
| --- | --- |
| 已发请求，收到可验证用量 | 按原请求登记输入、输出及支持的细分用量。即使业务结果未通过验证，已确认的实际用量仍记录一次。只有符合该模板用量协议的明确零才显示零。 |
| 发送前拒绝、取消或授权变化 | 原请求记录「未发送」，无厂商用量。没有发生发送就没有厂商用量证据。 |
| 回复丢失、用量缺失或前后矛盾 | 标记「用量待核实」。业务结果和用量状态分别按可信记录判断，原业务对有效结果与可恢复输出的规则继续适用。保留原调用编号和可用的安全关联证据。通过原调用键查回已经持久化的可信用量。现有人工补录只覆盖限定平台调用，首版自有文本沿原记录只读核实。原资料没有可信事实时保持待核实，需要人工补录的独立流程后续确认证据、授权和 CAS。缺失不能填零，不能自动用新 Key 或渠道重发。无点数预留待释放，也无账单待补扣。 |
| 本地保存回复丢失或重复补录 | 使用原调用键读回并比较已保存事实。相同事实重放继续返回原结果，矛盾报冲突。仅占位就崩溃或失去 ACK 时，在没有可靠发送或未发送事实前保留待核实。 |

## 验收条件

1. **自有无点数依赖。** 正常授权的企业自有 OpenAI 官方与受控兼容文本路径，用同一模拟厂商和隔离数据库验证。无适用参考价和汇率、企业余额为零、成员点数限额已用完三种单独及组合情况下，合格任务仍可发送。确认实际验证过每个已启用共用文本用途的入口及收尾，不能只测 Executor。至少覆盖 Chat 规划、已接线的店铺范围判断和内容任务，核对店铺范围的决策及故障分支不读取商业预留。原规划或业务配置中有明确的非货币预算时，验证仍按原上限拒绝超额请求。
2. **用量可查且点数账本无副作用。** 执行前后比对消费企业余额、预留、消耗、成员月点数、债务和点数流水。上述字段均不变化，无新增点数命令或预留。独立替身证实对自有调用未触碰商业预留或结算端口。已取得的实际用量可在本企业有权视图查询，跨企业及撤权读取被拒。
3. **失败情况下用量如实。** 覆盖未派发（无用量）、真实零、可信用量正常／业务结果无效、用量缺失、丢失响应、终态写入中断、重启后的原键重查与相同终态事实重放。主键去重，无额外外发，无伪造零和补扣，输出按原业务合同收尾。
4. **平台原账正确。** 相同型号和厂商同时配置平台与本企业自有渠道。平台渠道原有价格和汇率要求、余额约束、成员月限、正数预留、一次扣点、差额释放和结果未知留原预留逐项核对。冻结证据定量验证点数与原计算一致。
5. **切换与在途隔离。** 覆盖平台到自有和反向切换、Key 轮换、权限撤销、同名异源、已预留／已发／UNKNOWN。未发送的旧准备不能按新选择继续发，已发送的请求按原冻结方式收尾。伪造来源、计费方式、所属企业和零费率的客户端输入不能改变扣点资格。候选实现要证明更新顺序兼容原记录、已有预留仍按冻结路径收尾、暂停新增自有调用不会改写或错误重算现存事实。用旧预留和证明的测试数据逐字节比对原指纹，验证旧请求能按原规则完成一次收尾。
6. **页面区分费用。** 切换卡片和确认框清楚区分平台扣点和自有不扣。自有未配置参考价不会出现价格缺项提示。用量明细区分无用量、真实零、待核实和已知结果。已有平台点数用量流水保持含义。
7. **验证方式。** 以上实施验收均采用受控供应商或传输替身及任务隔离数据库。本批证据采用模拟厂商和隔离数据库。真实厂商调用及付费测试仍处于搁置状态。
