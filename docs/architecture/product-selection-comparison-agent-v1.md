## Explicit multi-candidate contract

Current `agent.Binding` is a comparable single-Product binding. Extend it with one omitted-when-zero fixed-size carrier, `Selection [5]SelectionProductRef`. A reference contains Collection item ID, its canonical positive item revision, ProductKey, original CatalogVersion and original PublicationID. Fixed-size keeps request/binding equality and existing guarded replay semantics; it is not a durable context table or opaque browser authority.

Only ContextKind `product-selection-v1` may carry this variant. It requires a real canonical UUID ContextID, TargetPlatform `product`, the single-product ProductKey/CatalogVersion/PublicationID fields empty, 2–5 unique candidate refs in sorted ItemID order followed by zero entries. Each ID/version/revision is bounded/canonical and duplicate Product refs are rejected. A normal single-Product binding must have zero Selection. Existing serialized requests retain their exact bytes because the zero carrier is omitted; no old request IDs or facts are rewritten.

The browser supplies only exact Collection selection inputs (item ID, expected revision, original version/publication from its existing scoped reads), context ID and request UUID. The trusted consumer rereads each original Collection item via `Select`, derives the ProductKey/source reference, reads/validates its exact Catalog publication, then constructs the binding. It never accepts client ProductKey, tenant, actor, member, price, stock or evidence as authoritative. A changed item/source invalidates new execution; selection must be prepared anew under a new explicit user intent, never silently remapped.

All existing consumers reject the selection variant through their exact context/profile/config checks. The text configuration owner accepts it only for this exact new definition/policy/prompt/profile; title/content/materials cannot consume it. The original Agent runtime fingerprints the complete comparable request/binding, so a same key with different candidate, revision, goal, mode, template or profile conflicts. No new idempotency store is introduced.

## Facts and recommendation semantics

The server produces the matrix: saved title/brand/category, bounded attributes/specifications, SKU attributes, explicitly disclosed variant price/currency and positive known stock, source warnings/review uncertainty, and exact candidate source version. At most 5 candidates, 32 facts per candidate, each value ≤512 UTF-8 bytes, aggregate inspect JSON ≤32 KiB. Long fields are explicitly omitted rather than silently truncated into a new complete fact. Do not include arbitrary source metadata, private provider URLs, credentials, model instructions or remote image fetches.

Evidence identities bind the candidate item/ref, exact field path and canonical whole value/hash. Numeric prices are rendered with their original currency; no mixed-currency ranking/conversion. A missing price/currency remains unknown. The current snapshot stock scalar cannot distinguish absent from zero, so zero is UNKNOWN, not proof of no stock. Source-inferred fields and warnings remain visible as uncertain. Recorded data is not a guarantee of today's supplier availability. Missing sales, demand, shipping, platform commission, tax and full landed costs stay unknown; no fabricated profit or sales metric is permitted.

Strict proposal: bounded overview, an optional recommended candidate item ID, and 1–5 candidate assessments. Each assessment uses that selected ID, bounded advisory text and 1–6 exact evidence IDs belonging to the candidate; unsupported ranking/financial fields are rejected. Cross-candidate comparison citations are explicitly represented, cannot borrow an undisclosed candidate. Factual quotations are rendered from deterministic disclosure, never model-authored numeric text; advisory text is separately labelled “AI建议”. The server's missing-information list is always shown alongside model advice. The validator proves identities and citations, not the commercial quality of advice; that limit is explicit in the UI and handoff, not a claim of independent product acceptance.

Without model route/credentials or explicit activation, users can inspect authorized facts and see NEEDS_CONFIGURATION/NOT_ENABLED for analysis. Do not borrow title/content/materials profiles or turn a sample into a successful analysis. Template support, if selected, is exact selection schema with bounded criteria text and fixed product platform, no KnowledgeBase or content/image fields. Template revision is frozen and revalidated like other registered text consumers; no default-created templates or config aliases. The existing explicit configuration initializer may extend only its admitted template checks/typed parameter payload, using a selection-only option; serving verifies without modifying schema. Preserve all previous exact schema variants and rows, no new table or automatic installation.
