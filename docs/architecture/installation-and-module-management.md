## 1. 用户结果与范围

一套本机安装管理界面，按实例是否已安装选择入口：

| 入口 | 用户操作 | 成功结果 |
| --- | --- | --- |
| 首次安装 | 环境检查 → 选择已有安装组合 → 填写配置 → 预览并确认 → 安装进度 | 新独立Compose project正常启动，提供当前HTTPS入口及原身份系统的管理员交接 |
| 管理现有实例 | 查看真实模块状态 → 查看缺项 → 配置 → 检查及变更预览 → 确认应用 | 对准确实例应用配置，按需重启准确服务，核对健康和实际模块就绪，原数据保留 |

首版面向当前本机Docker部署；同一套模块定义、表单、检测和预览复用，不创建两个安装系统。业务工作台继续使用现有页面，安装管理不嵌入日常经营表单。遵守当前Figma仅流程参考决定和现有设计系统；安装向导只按真实依赖分步。

Must：首次安装只能指向新空项目；保留实例绝不进入空库初始化。原身份、企业、模块权限、数据、图片、任务、凭据和未决资源预留保持。配置与安装、安装与启用、启用与可执行分开。只有原owner验证成功且实际运行就绪，才能显示可用。

Out of Scope：远程集群/生产部署平台、任意脚本/SQL/Compose编辑器、动态插件安装框架、自动授予企业权限、自动登记真实店铺/模型/支付、推理/采集/发布/资源发放或释放、导入演示业务数据、自动数据迁移/删除/回灌、通用分布式事务/恢复框架。首版不改变现有原生安装与维护合同；不支持的安装组合如实不可选，不因有界面就放宽。

无新增Accepted Risk。Threat Model针对跨站访问本机管理、选错实例/owner、泄露凭据、首次安装误碰非空数据、同一操作并发或重放、配置漂移与服务重启失败；不扩大为管理任意主机/恶意宿主管理员或改写已接受的领域风险。

## 2. 已有能力和真实缺口

- `deployments/docker/account-compose/{compose-modules,bootstrap,native-modules-init}.sh` 已有新空安装、固定模块顺序、私密状态和保留重启合同。bootstrap检测marker并拒绝给保留项目补装新空profile；native安装中断后原合同拒绝自动重放。**不能直接把这些命令加到现有实例的“启用”按钮上。**
- 各`cmd/*-schema-init`及原owner已批准的有界维护负责schema/grants；普通`current-application`只验证。已有新装与维护入口不一致时，界面显示真实阻碍，不复制DDL或给运行角色提升权限。
- `internal/app/runtime/currentapplication.Config/LoadConfig`与各模块validate、既有HTTP装配、UI注入开关、原版本/receipt是现有部署依据。授权catalog是成员权限事实，不能用它推导模块已安装/已配置。
- `scripts/build-listingkit-images.ps1`已有准确Git源码镜像receipt；Compose已有明确profile和保留操作入口。安装界面消费已准备且验证的版本，不自行构建一条旧镜像继承链。
- 原35444只读样本：AIWorkbench配置存在但enabled=false，正式SupplyChain缺配置且Store官方应用数为0；这与ProductAgent已启用、研究入口存在、本地测试草稿可用是不同事实。不能因为有菜单或Agent配置就标记全模块可执行。该样本不作为新装默认值或本轮执行授权。

## 3. 唯一控制边界与放置

增加一个**显式由宿主操作者启动、仅本机可达的安装控制进程**，负责本轮安装会话，不放入普通业务serving进程。界面由该控制进程同源提供；复用现有React/设计系统表单、严格DTO和状态反馈。执行仍调用既有Compose/owner入口，不建设新的部署引擎。同一本机工具保留可启动的“安装与维护”入口，首次安装后再次打开进入实例模块管理，不要求用户手工编辑JSON或运行新空初始化。

正常业务API、Next BFF和普通租户会话不获得Docker socket、shell、数据库owner或ZITADEL bootstrap凭据。业务工作台可向有资格的平台维护者展示安装管理入口说明；链接本身不提供安装权限。首版通过宿主启动的当前本机界面管理实例，不开放远端浏览器控制。

首次业务身份尚不存在时，安装权限来自**宿主显式启动和一次性配对**，仅用于安装控制，不伪造业务user/org/member。ZITADEL始终是唯一业务身份owner，管理员创建沿原bootstrap；已有实例的企业管理员或platform_admin身份本身不能取得宿主维护权限。管理端不代用户执行企业启用、角色分配或provider授权。

控制监听literal loopback、随机可用端口；绑定准确Host/Origin、独立短时安装会话、SameSite严格cookie、CSRF检查、禁止CORS/嵌入。配对秘密只在宿主交接，不放URL/query/history或业务页面；同源HTTPS就绪前不提交外部provider秘密。TLS与信任建立沿已有本机安装流程，证书确认仍由用户完成，不自动绕过浏览器安全提示。失效/退出后停止接受mutation。

首次TLS/身份尚未就绪时，表单只收集非秘密结构字段及受限私密文件引用；新owner口令沿原bootstrap在本机生成，不经未就绪的业务表单传递。provider秘密在原HTTPS和正常凭据入口就绪后按原owner登记。原native-modules-init含psql变量携带ownerpassword进入argv的实现，不能声称直接复用就满足上述秘密边界；实施时须在本轮实际调用链改为私密stdin/file输入，并验证所有实际消费的bootstrap/owner入口，未消费的CLI不在此扩大改造。

安装进程只持有所选实例的维护凭据，调用原installer后释放临时引用；runtime继续最小权限。秘密经原private文件/凭据owner登记，不进入sessionStorage/localStorage、日志、报告、命令参数或浏览器回显。界面只显示是否已登记及非敏感名称；模型/店铺等已有配置继续链接原正式配置页。

## 4. 配置与状态事实

部署配置仍以当前准确实例的私密manifest、完整Compose组合/环境和对应image receipt为依据；不引入第二份“模块启用状态表”。安装控制的命令回执记录执行过程及引用的配置hash，不替代实际运行事实。

新增有限、随程序版本发布的安装模块描述是**当前合同的展示/调用元数据**：模块ID、显示名、原Config字段及前端开关、依赖、允许profile、既有检查/初始化/维护入口。它不包含installed=true事实、不生成业务权限、不接受远程下载的脚本或用户输入的命令。直接引用现有owner/validator，检查接线一致性，不能复制一套schema或provider规则。

模块列表同时显示以下独立事实，不把所有情况压成一个开关：

- 已安装/未安装/当前无法核实：当前owner只读schema及权限校验。
- 已配置/缺配置：原Config/原凭据登记的必要字段，秘密仅显示存在性。
- 已启用/未启用：准确后端装配和前端注入，前后不一致须显示差异。
- 可使用/受阻：原健康、依赖、企业权限/配额/provider就绪；无法读到的范围标待核实。

“缺少模型”“缺少官方店铺”“缺运行权限”“未开启”“仅本地测试”分别显示。查看页面、检查本机依赖和预览不执行付费调用、真实取数、provider授权或发布。无法安全只读验证的外部能力保持待配置/待用户验证，不能用一次真实调用当隐式安装测试。

检测只用严格配置解析、Docker元数据和原owner明确的只读验证端口；不得调用完整runtime.Run（会装配并启动worker）、Compose up、bootstrap或installer来“探测”。没有合格只读端口时显示待核实，不能以试运行补证。保留实例的完整私密overlay及其env/命令是准确调用依据，不能用会cd自身目录、固定读取.env和组合的compose-modules.sh替换。

## 5. 两条完整操作路径

### 5.1 首次安装

1. 宿主显式启动安装界面；完成本机配对。展示实际Docker状态、空间、端口占用、已准备版本及明确的新项目名称/目录。
2. 只选择当前已有且允许的新装组合；依赖由原profile规则检测并明确展示。核心身份/权限/资源owner按现有合同必需，不能取消后假装完整应用已安装。
3. 用户填写公开地址、端口、私密配置文件位置等结构字段；秘密使用现有私密输入入口。预览准确project、volumes、版本、安装组合及尚未配置的外部服务。
4. 确认后再次检查准确项目/目录/数据库/卷是否为新空目标；有现有数据或marker就拒绝，不自动改名、清空或变更到另一实例。
5. 沿原Compose/bootstrap/owner顺序执行，显示真实阶段和原回执；只生成既有安装事实，不生成业务测试数据。
6. 原schema/权限及健康检查通过，交出当前HTTPS入口和原身份bootstrap私密交接。外部能力未配置不阻止合格基础安装，也不标为可用。

### 5.2 管理现有实例

1. 宿主显式选择一个具体保留实例；展示准确project/服务ID、origin、当前image与配置版本。读取当前有效组合，不能拿仓库默认模板覆盖私密overlay。
2. 选模块查看依赖、缺项和既有配置入口。已安装模块只准备配置差异；没有合格保留库维护入口的缺schema模块显示“需要现有owner维护”，不能使用新空installer。
3. 预览当前→候选配置、需重启的准确服务、保留的数据/卷与可用回退条件；依赖变化要重新检查，不能静默启用其它模块。停用仅停止对应新入口/执行，不删表/数据、撤销既有业务身份或释放未决预留。
4. 确认应用绑定准确实例、当前配置hash、candidate hash、镜像receipt、稳定命令key；全局最多一个实例变更执行，同一实例外部漂移拒绝覆盖。
5. 复用已有备份/维护入口。只有准确owner明确支持的有界维护才可执行；不拆写DDL/GRANT，不调用旧空库初始化。按候选完整组合仅更新必要服务，保留网络、命令、凭据、私密mount、identity与卷。
6. 读实际schema/权限、服务健康、后端装配/前端开关；成功后才显示“已应用”。失败/未核实保留原计划和回执，不把HTTP成功当服务就绪。

## 6. 命令、并发和失败边界

本机安装控制只新增一个有界安装操作记录：ID/key、准确instance identity、完整输入digest、原配置及候选配置hash、各原命令引用/结果、最终核对结果。记录保存在安装进程的私密工作目录，原manifest和owner数据仍是事实owner。凭据只存引用，结果严格脱敏。

展示状态：待确认→执行中→已核对完成；执行失败或响应不明分别保留原结果/待核实。原子写入本机意图后才派发；同key同digest读同回执，同key不同digest拒绝。执行进程通过OS文件锁持有准确实例排他权，重启不把遗留执行中记录当新操作；不能因为PID消失就推断未执行。

私密操作目录与锁绑定稳定的canonical实例身份（准确Docker context、project和已核实的实际资源绑定），不按浏览器会话、临时输出目录或新进程生成。所有控制会话和重启复用同一实例目录、原key和排他锁；配置路径/别名指向同一实际实例时也不能创建第二套操作记录。无法确定唯一实例身份或安全读取原记录时拒绝mutation，不允许换目录或key绕过。并发/重启测试必须跨控制进程，不能只在一个handler内用内存锁证明。

配置文件使用新的私密候选目录，先完整校验与落盘，不逐字段覆盖当前manifest。原配置路径/镜像保留；Compose应用不是跨DB/多服务事务，不声称原子安装。当前原生installer已有的事务和中断拒绝合同继续有效。

- 派发前失败：未执行，保留草稿供修正；改变输入产生新的明确计划。
- owner安装失败/响应丢失：沿原命令/owner状态核实，**不自动重跑**。原owner没有安全恢复合同就停止，并准确指出哪个原入口需处理；不由通用管理器发明补偿。
- 宿主/控制进程重启：按原key读取实际Compose/原owner状态；未核实前禁止新的冲突应用。继续必须沿原明确合同，不能换key重放初始化。
- 候选健康失败：只有该组合的原schema/数据合同明确允许时，才能切回原镜像和配置；不自动restore旧dump覆盖运行期间业务写入。
- 原schema有不可逆/不可安全回退变化，或已出现新持久事实：保持待处理，沿原owner维护；不删除记录、降级表或假报“已回退”。

回退能力必须是计划前置检测的真实结果，“有备份”不等于自动可回退。首次失败保留新项目及状态供核实，禁止自动destroy/down -v。

## 7. Contract → implementation → injection → consumer

| 合同/owner | 实现位置与复用 | 控制/界面消费者 |
| --- | --- | --- |
| 本机安装权限/有界操作记录 | 新独立setup command/control包，私密会话、锁和原命令引用 | 同源安装UI，两种入口复用；不注入业务runtime |
| 实际配置、依赖、版本 | currentapplication Config/validate、现有Compose profile、source receipt | 只读检测→配置计划，调用已批准构造器/原检查，不复制规则 |
| 新空初始化 | account-compose bootstrap/native-modules-init和原owner CLI | 首次安装专用执行分支；保留实例入口无法选择 |
| 保留库有界维护 | 每个现行owner已批准的maintenance CLI | 缺schema检查映射准确入口；缺入口时拒绝，不新增通用DDL |
| 凭据、业务授权、模型/店铺配置 | 现有private files、credential/Store/Agent owner与ZITADEL | 非敏感状态/现有正式配置入口；不把宿主权限转为企业业务身份 |
| 程序启停/回退 | 当前准确Compose组合、备份与已验证回退入口 | 白名单参数数组调用原工具；无任意shell/API命令 |

Implementation cut按同一用户结果维护一个主要PR，先完成准入，再实现完整的新装与已有实例配置路径；不为每个列表/表单/接口机械拆PR。本地安装/配置控制属于新增高风险边界，最终必须检查真实diff和调用路径。

## 8. 实施验证与交付

只复用现有测试/隔离资源入口，不建设新runner：

1. 只读检测/表单：真实未配置/未安装/未启用/权限或外部缺项可区分；秘密不回显；无模型/采集/业务mutation。桌面/窄屏、键盘、错误、返回后草稿保留。
2. 新空安装：独立新project成功交出原正常登录入口，schema/权限由原owner校验；非空/误选保留项目在执行前拒绝；中断不重复初始化。
3. 原库隔离副本管理：配置→预览→应用→健康→刷新，实际模块可用；同一数据/权限/图库/任务/原预留保留；不把前端flag当通过。
4. 原key/并发/漂移/重启/失败：只派发一次，旧计划不足时拒绝，UNKNOWN只核实，按准确回退合同处理，不覆盖并发业务新写。

原35444、真实provider/支付/发布、模型调用和用户验收均单独标NOT_RUN，不能由副本或CI绿推断。正式代码开工前须独立Architecture Review达到IMPLEMENTATION_READY。Legacy decision: N/A；这是当前系统显式安装/配置，不新增旧系统兼容或迁移。
